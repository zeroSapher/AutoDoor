### 0.2 ⚠️ 必须澄清："90.0°" 与直流电机的矛盾

原题"开门限位（默认 900）"，经确认为 **90.0°**。但本方案用的是**直流电机 + 开环**，
这带来一个必须正面处理的矛盾：

> **直流电机开环没有角度反馈源，无法保证绝对角度。** 没有编码器，
> 固件根本不知道门转到了几度。

**解决方案：用限位开关把"90°"物化成机械位置。**

```
开门限位开关的安装位置 == 门体转到 90° 的物理位置
=>  "开门到位" 等价于 "门体到达 90°"
```

这样"默认 900"不再是固件里一个抽象数，而是一个**可安装、可调整、可复现的机械基准**。

**但必须接受的工程事实**：限位触发点会随门体惯性、过冲和机械磨损漂移。
所以机械设计上必须做到：

1. **留过冲余量** — 门体到限位后不能硬顶，要有柔性止挡（橡胶垫 / 弹簧）
2. **限位安装位置可调** — 用长腰孔，装好后现场标定一次
3. **固件加超时兜底** — 开/关门超过 5 s 未到限位 → 立即停机 + 上报告警

**如果日后需要"每次严格 90.0°"**，可选路径：SG90 舵机（直接指令角度，你清单里有）
或带编码器的直流电机（闭环 PID）。**本方案采用"限位即 90°"的折中** ——
这是在使用直流电机的前提下唯一可行的做法。

## 1. 硬件方案

### 1.1 系统框图

```
                      5V ──┬──[ 开门限位 NC ]──[ 关门限位 NC ]──┐
                           │        (硬件断电路径，串联)        │
                           │                                   ▼
   门外检测 ─PB12┐         │                            ┌─────────────┐
   (按键模拟)    │         │                            │   L9110S    │
   门内检测 ─PB13┤         │        PA4 (IA) ──────────▶│  双路 H桥   │
   (按键模拟)    │         │        PA5 (IB) ──────────▶│  (用 1 路)  │
                │         │                            └──────┬──────┘
   开门限位 ─PA0─┤         │                                   │ OA / OB
   关门限位 ─PA1─┤         │                                   ▼
   KEY ×4  ─PB5..PB8─┐    │                            ┌─────────────┐
                     │    │                            │  130 电机   │
                     ▼    │                            │  (3–6V 玩具)│
        ┌─────────────────────────┐                     └─────────────┘
        │    STM32F103C8T6        │
        │        72 MHz           │──USART1(PA9/PA10)──▶ USB-TTL ──▶ PC 上位机
        │                         │
        │                         │──USART2(PA2/PA3)───▶ [预留：HC-05 蓝牙]
        │                         │
        │  PB3 ─▶ 有源蜂鸣器       │
        │  PB4 ─▶ 状态 LED         │
        └───────────┬─────────────┘
                    │ I2C (PB10/PB11, 软件)
              ┌─────┴──────┬──────────────┐
              ▼            ▼              ▼
          OLED 0.96"   AT24C32 EEPROM   [预留：DS3231 RTC]
```

> **注意限位开关的接线位置（安全关键）**：两个限位开关的 **NC 触点串联后，
> 接在 5 V 到 L9110S 的电机供电（VM）路径上**。
> 任一限位触发 → 电机供电被**物理切断** —— 这才叫"确保不超程"。
> **绝不要把限位开关串在 H 桥的电机输出（OA/OB）线上**：那会让电机电流被迫
> 走 H 桥内部体二极管，可能在换向瞬间形成直通短路。切**供电**是正确做法。
>
> 同时电机输出端必须并 **SS34 续流二极管**（或 100 nF + 10 Ω 阻容吸收），
> 泄放断电瞬间的感性反峰。

### 1.2 关键器件选型

#### 电机驱动：L9110S 双路 H 桥模块（清单实物）

| 参数 | 值 |
|---|---|
| 通道 | 双路 H 桥（本设计用 1 路） |
| 电压 | 2.5–12 V（本设计 **5 V**） |
| 电流 | 每路连续 **800 mA** / 峰值 1.5 A |
| 控制 | **每路仅 2 个引脚**：`IA` / `IB` |
| 压降 | **约 0.3–0.5 V**（远优于 L298N 的约 2 V） |

**IA/IB 真值表**（这是 L9110S 的特点：没有独立使能脚，靠两脚电平组合控制）：

| IA | IB | 电机状态 |
|---|---|---|
| 0 | 0 | 停止（**两下管都关断，电机自由滑行**） |
| 0 | 1 | 正转 |
| 1 | 0 | 反转 |
| 1 | 1 | **刹车（两下管都导通，电机被短路制动）** |

**为什么选 L9110S 而不是清单里的 L298N**：

| 对比项 | L9110S | L298N |
|---|---|---|
| 占用引脚 | **2 个** | 3 个（IN1/IN2/ENA） |
| 压降 | 0.3–0.5 V | 约 2 V |
| 对 6 V 的 130 电机 | 电机实得约 5.5 V ✅ | 电机实得约 4 V，偏弱 ⚠️ |
| 驱动能力 | 800 mA | 2 A |
| 体积 | 小 | 大、带散热片 |

对**桌面模型 + 130 玩具电机**（堵转电流通常 < 500 mA）而言，L9110S 的
800 mA 完全够用，而且**省下 1 个引脚、压降小 1.5 V**，是更合适的选择。

**关于"上下管直通"**：L9110S 与 L298N 一样**不内置死区**。但本设计的 PWM 打在
`IA`/`IB` 上（而非独立使能脚），**换向时固件必须遵守"先刹车/停止，再换向"**：

```c
/* 换向前必须先让 IA=IB=0 或 IA=IB=1 保持一段死区时间 */
Motor_Stop();          /* IA=0, IB=0 */
Delay_ms(20);          /* 死区：确保电机电流归零 */
Motor_SetDir(dir);     /* 再换向 */
```

软启动的斜坡逻辑里本来就要做这一步，所以不增加额外复杂度，但**代码里必须显式体现**。

#### ⚠️ 130 直流电机的电压限制

清单里的是 **130 玩具电机**（配扇叶），**额定 3–6 V**：

| 项目 | 值 |
|---|---|
| 额定电压 | **3–6 V（绝对不要给 12 V，会烧）** |
| 空载电流 | 约 50–80 mA |
| 堵转电流 | 约 300–500 mA |
| 空载转速 | 约 6000–12000 rpm（需减速机构） |

**供电方案**：5 V 直供（L9110S 压降 0.3–0.5 V，电机实得约 4.5–4.7 V，处于额定区间内 ✅）。

> 130 电机转速很高、扭矩很小，模型门必须**加减速机构**（齿轮/皮带/蜗杆）。
> 直接用电机轴驱动门体是转不动的 —— 这是模型搭建时最容易忽略的一点。

#### 限位开关：KW12-3 微动开关（清单实物）

| 参数 | 值 | 说明 |
|---|---|---|
| 型号 | **KW12-3**（带长柄，清单中 3 个） | 小手柄微动开关 |
| 触点形式 | **1NO + 1NC**（三脚：COM / NO / NC） | **必须用 NC 触点** |
| 额定 | 5 A @ 125 VAC | 信号用途余量极大 |
| 动作力 | 约 0.5–1.6 N | 轻 |
| 机械寿命 | ≥ 100 万次 | 模型演示足够 |

**三脚识别**：`COM` 为公共端；**NC = 常态闭合（不按导通）**；`NO = 常态断开`。

**⚠️ 必须接 NC（常闭）触点** —— 这是本设计的核心安全原则：

```
用 NO 触点：门到位置 -> 开关闭合 -> 才去切断电机
             ↑ 断线 / 接触不良 / 开关损坏 => 永远不闭合 => 保护完全失效

用 NC 触点：门到位置 -> 开关断开 -> 切断电机
             ↑ 断线 / 接触不良 / 开关损坏 => 断开 => 自动进入保护生效状态
```

即 **故障导向安全（fail-safe）**。任何一处失效（线断了、接头松了、开关坏了），
结果都是"电机停"，而不是"电机继续冲"。

**接法**：`COM` 接 5 V 进线，`NC` 接下一级（另一个限位开关的 COM，最后到 L9110S 的 VM）。
两个限位**串联**，任一断开即切断电机供电。

**同时也接到 MCU**（`PA0` / `PA1`）用于状态检测与记录：NC 常态导通 → 引脚被
10 kΩ 上拉+开关接地读为低；触发断开 → 读为高。**加 100 nF 到地做硬件消抖。**

#### 人员检测：本阶段用按键模拟（清单无合适传感器）

清单里只有 **TCRT5000 寻迹模块**，它是**反射式近距传感器，有效距离约 1 cm**，
**无法检测"人员靠近"**（人站到门边时传感器早已贴上衣服）。

**本阶段方案**：

| 信号 | 实现 | 真实传感器接口 |
|---|---|---|
| 门外检测（进门） | **按键模拟**，接 `PB12` | 预留，EXTI12 |
| 门内检测（出门） | **按键模拟**，接 `PB13` | 预留，EXTI13 |

**为什么这样安排是合理的**：

1. **接口完全一致** —— 按键和真实红外传感器都是"下降沿 + 消抖"的 EXTI 输入，
   换成 E18-D80NK 时**只需改 `main.h` 的引脚宏，固件逻辑一行不改**
2. 门控状态机、限位保护、关门延时、日志记录**全部可以完整实现并验证**
3. 不阻塞开发进度

**TCRT5000 的正确用途**（合理利用手上的器件）：在门体转轴贴一小块**反光贴**，
转到 90° 时对准传感器，可做**非接触式位置确认**，作为限位开关的冗余校验。

**日后升级**：补购 **E18-D80NK**（约 8 元/个，检测距离 3–80 cm 可调）即可获得
真实人员检测能力。

### 1.3 电源方案

130 电机额定 3–6 V，所以**整套系统用 5 V 单电源**即可，不需要 12 V。

```
5V / 2A 电源（或 4 节 AA 电池 6V 经 AMS1117-5.0 降压）
   │
   ├──> [开门限位 NC] ── [关门限位 NC] ──> L9110S VM (电机供电)  ← 硬件断电路径
   │                                          └ 470 µF + 100 nF 就近去耦
   │                                          └ SS34 续流二极管（跨接 OA/OB）
   ├──> L9110S VCC (逻辑供电，不经限位开关！)
   ├──> OLED / AT24C32 / 蜂鸣器 / 按键上拉
   └──> AMS1117-3.3 ──> 3.3 V ──> STM32 / 限位开关上拉 / LED
```

> **⚠️ 关键：限位开关只切"电机供电 VM"，不能切"逻辑供电 VCC"。**
> 如果连逻辑电源一起切断，MCU 会在限位触发瞬间掉电，
> **状态机无法记录"因限位而停止"这一事件**，串口也发不出报告。
> L9110S 的 VCC / VM 是分开的，正好支持这种做法。

| 要点 | 做法 |
|---|---|
| **地线** | **星形接地**：电机大电流回流直接回电源入口，**不经过 MCU 地平面** |
| 电机去耦 | 电机端子并 **470 µF 电解 + 100 nF 陶瓷** |
| 电机续流 | 跨接在 L9110S 的 `OA`/`OB` 之间并 **SS34 肖特基**（泄放断电感性反峰） |
| MCU 去耦 | 每个 VDD 脚配 100 nF，另加 10 µF 体电容 |
| 晶振 | 8 MHz + 22 pF ×2，**走线尽量短，包地** |
| 限位/按键 | 10 kΩ 上拉 + **100 nF 到地**（硬件消抖，减轻软件负担） |
| 电流预留 | 5 V 电源按 **≥ 1 A** 选（130 电机堵转约 0.5 A + 逻辑与 OLED 约 0.15 A，留约 50% 余量） |

> **EMC 提醒**：电机是强干扰源，是这个系统里最大的可靠性风险。
> 软件消抖救不了电气干扰，**去耦和接地必须在 PCB 上做对**。
> 130 玩具电机还常带**电刷火花**，`OA`/`OB` 上的 100 nF 陶瓷电容尤其不能省。

## 2. 引脚分配

### 2.1 ⚠️ 为什么必须现在就把引脚定死

STM32F1 的 EXTI 有一个硬约束：**PA0 / PB0 / PC0 共用 EXTI0**，同编号的引脚
**只能选一个**做外部中断。本系统需要 **8 路外部中断**（2 限位 + 2 红外 + 4 按键），
所以这 8 个引脚**必须落在 8 个不同编号上**。这是 PCB 布线前就必须冻结的约束，
改一个编号就可能牵动一片。

> **这条规则在 round 1–10 里一直是违反状态。** 原分配把红外放在 `PB0/PB1`，
> 与限位的 `PA0/PA1` 撞在 EXTI0/EXTI1 上。AFIO 每条线只能选一个端口，而
> `Sensor_Init()` 在 `Limit_Init()` 之后执行，于是**两条线都被传感器拿走，
> 限位一个中断都没有** —— 而且没有任何报错：所有调用点都用 `(void)` 丢掉了
> `Exti_ConfigPin()` 的返回值。限位 ISR 里那两句 `Motor_EmergencyStop()`
> 是**不可达代码**。
>
> 现在：红外改到 `PB12/PB13`（EXTI12/13），并在两处加了会失败的检查 ——
> `main.h` 的编译期断言（编号重复直接编译不过）与 `Exti_ConfigPin()` 的运行时
> 拒绝重映射 + 上电冲突计数。**规则写在注释里已经失败过一次，所以现在它是可执行的。**

### 2.2 分配表

|---|---|---|---|---|---|

#### 电机 PWM 的实现方式（TIM3 保留给硬件 PWM）

L9110S 没有独立使能脚，所以 PWM 必须打在 `IA`/`IB` 上。这里有两种做法：

| 方案 | 引脚 | 优点 | 缺点 |
|---|---|---|---|
| **软件 PWM（本设计采用）** | `PA4`/`PA5` 普通 GPIO | **省下一个定时器**，引脚可自由选 | 占 CPU（20 kHz 太高，实际用 **1 kHz**） |
| 硬件 PWM（备选） | `PA6`(TIM3_CH1) / `PA7`(TIM3_CH2) | 不占 CPU，波形精确 | 占用 TIM3 |

**本设计采用软件 PWM**，理由：

1. **桌面模型门对调速平滑度要求不高**，1 kHz 足够（远高于机械响应时间常数）
2. **把 TIM3 完整保留**，留给后续扩展（急停输入捕获、独立看门狗节拍、蓝牙超时）
3. 实现方式是**在 SysTick 的 1 ms 中断里累加相位**，得到 1 kHz、100 级分辨率的 PWM ——
   这**正是题目要求的"定时器中断用于电机 PWM 调速"**，完全吻合

> 若要改用硬件 PWM，只需把 `PA4`/`PA5` 换成 `PA6`/`PA7` 并启用 TIM3，
> 上层 `Motor_SetSpeed()` 接口不变。`main.h` 里已把引脚做成宏，切换成本很低。

### 2.3 ⚠️ 两个必须注意的坑

**坑 1：PB3 / PB4 默认被 JTAG 占用。**

复位后 JTAG 使能，PB3 = JTDO、PB4 = NJTRST。要用作普通 GPIO，
必须在 `main()` 最开头（**在任何 GPIO 配置之前**）执行：

```c
RCC_APB2PeriphClockCmd(RCC_APB2Periph_AFIO, ENABLE);
GPIO_PinRemapConfig(GPIO_Remap_SWJ_JTAGDisable, ENABLE);  /* 只关 JTAG，保留 SWD */
```

用 `SWJ_JTAGDisable` 而**不是** `SWJ_Disable` —— 后者会把 SWD 也关掉，
**之后就再也连不上下载器了**（只能靠上电瞬间的特殊时序救回来）。这是一个经典陷阱。

**坑 2：SWD 引脚绝对不要挪作他用。** `PA13/PA14` 一占，ST-Link 就连不上。

### 2.4 OLED / EEPROM 为什么改到 PB10/PB11

原 DHT11 工程用的是 PB6/PB7。本设计把 I2C 挪到 **PB10/PB11**，原因：
**PB6/PB7 需要腾出来给 KEY2/KEY3**，否则按键的 EXTI 编号会和别的引脚撞车。

> 代价：原工程的 I2C 引脚定义在 `Core/main.h`，改动只涉及那个文件，驱动层无感。

## 3. 定时器分配

### 3.1 分配表

| 定时器 | 用途 | 频率 | 说明 |
|---|---|---|---|
| **SysTick** | 1 ms 系统滴答 | 1 kHz 中断 | 状态机、倒计时、超时、事件时间戳、**软件 PWM 相位累加** |
| **TIM4** | 微秒时基 | 自由运行 1 MHz | 已被 `Delay.c` 独占，**不可复用** |
| **TIM3** | **保留** | — | 备选：改用硬件 PWM（`PA6`/`PA7`）或后续扩展 |
| TIM1 / TIM2 | **保留** | — | 后续扩展：急停输入捕获、独立看门狗喂狗节拍、蓝牙超时 |

> **本设计不使用硬件 PWM** —— 电机调速由 SysTick 中断里的软件 PWM 实现（见 2.2 节末），
> 因此 TIM3 完整保留。这正好落实题目"定时器中断用于电机 PWM 调速"的要求。

### 3.2 ⚠️ 为什么微秒时基（TIM4）绝对不能被挪用

原工程的 `Delay.c` **已经独占 TIM4** 做微秒延时。
如果把别的用途（无论是 PWM 还是延时）也放到 TIM4 上，两者会互相破坏：
改 `PSC/ARR/CCR` 会让微秒延时立刻失准。

**所以任何新增的定时需求都必须用别的定时器，绝不能复用 TIM4。**
这类"定时器被悄悄共用"的问题，现象是"电机一动就出错"，极难排查，
必须在设计阶段就划清。

### 3.3 软件 PWM 的实现（1 kHz，100 级分辨率）

在 SysTick 的 1 ms 中断里累加相位，每 1 ms 输出一个 1 kHz 周期：

```c
/* SysTick_Handler 内，由 1ms 节拍驱动 */
static uint8_t pwm_phase = 0;      /* 0..99 */
static uint8_t pwm_duty  = 0;      /* 0..100，目标占空比 */

static void swpwm_tick(void)
{
    const uint8_t STEP = 10;       /* 每 1ms 走 10 步 => 100 步/10ms => 1 kHz */

    pwm_phase = (pwm_phase + STEP) % 100;
    Motor_ApplyPhase(pwm_phase < pwm_duty);   /* 置 IA/IB 电平 */
}
```

**为什么是 1 kHz 而不是 20 kHz**：

| 频率 | CPU 开销 | 适用性 |
|---|---|---|
| 1 kHz | 每 1 ms 一次中断，**开销可忽略** | ✅ 桌面模型门足够，机械惯量远大于 1 ms |
| 20 kHz | 需 20 µs 一次中断，72 MHz 下仅 1440 周期/次，**CPU 会被吃满** | ❌ 软件 PWM 做不到 |

硬件 PWM 之所以能用 20 kHz，是因为**波形由定时器硬件产生、不占 CPU**。
软件 PWM 受限于中断开销，必须选低频。对模型门而言 1 kHz **完全够用且听觉上
仍有轻微嗡声但音量很低**；如果实测啸叫明显，可提高 SysTick 无关的独立方案
（改用 TIM3 硬件 PWM，`PA4/PA5` → `PA6/PA7`，接口不变）。

**换向死区**：`Motor_ApplyPhase()` 在方向翻转时**必须先让 IA=IB=0 保持 ≥1 ms**
（即至少一个 SysTick 周期）再给新方向，避免 H 桥上下管瞬态直通。

### 3.4 软启动（必须做）

占空比从 0 线性斜坡到目标值（例如 **400 ms 内 0→70%**）：

- **避免机械冲击**：门体不会"猛地一窜"
- **避免电流尖峰**：直流电机堵转电流可达额定的 5–10 倍，缓启动能显著降低对电源的冲击
- **保护 130 玩具电机**：这类电机电刷很脆弱，硬启动会加速磨损

停止时同样做斜坡降速（约 200 ms），否则门体撞击限位的动能全部由机械结构吸收。

```c
/* 软启动：每 1ms 调一次，400ms 斜坡到目标 */
if (motor.ramping && (++motor.tick >= 1)) {
    motor.tick = 0;
    if (motor.duty < motor.target) motor.duty += 1;   /* 100 级 / 400ms */
    else motor.ramping = 0;
}
```

### 4.1 状态定义

| 状态 | 含义 | 电机 | 蜂鸣器 | 状态 LED |
|---|---|---|---|---|
| `INIT` | 上电自检 | 停用（`IA=IB=0`） | 短鸣 1 声 | 快闪 3 次 |
| `IDLE` | 门关闭且锁定 | 停用 | 静音 | 常灭 |

|---|---|---|---|

| `INIT` | 自检失败 | `STOPPED` | 上报故障码 |
| `IDLE` | 门外红外触发（有人进） | `OPENING` | 启动正转，开定时器，记日志 |
| `IDLE` | 手动开门键 | `OPENING` | 同上（手动模式） |
| `OPENING` | **开门限位触发** | `OPEN` | 停机，**启动自动关门倒计时** |

| `CLOSING` | 超时 5 s 未到限位 | `STOPPED` | 停机，上报"关门超时"故障 |

| `STOPPED` | 启停键短按 | `INIT` | 重新自检 |

### 4.3 ⚠️ 中断优先级设计（安全性核心）

```
抢占优先级   0  ──  开门限位 / 关门限位      ← 最高，任何情况都不能被延迟
             1  ──  SysTick / USART1 / USART2
             2  ──  红外传感器（门外/门内）
             3  ── 按键（最低，人类反应速度）
```

**为什么限位必须高于红外**：红外触发只是"想开门"，而限位触发是"再不停止就撞坏了"。
两者同时到来时，限位必须赢。这正是原题"限位信号…优先级高于传感器信号"的落实。

**为什么所有 EXTI 都必须软件消抖**：机械触点在闭合瞬间会产生 **5–20 ms 的抖动**，
一次按下会被识别成几十次中断。做法：中断里只置标志 + 记录时间戳，
由 1 ms 的 SysTick 任务在 20 ms 后确认电平仍有效才认为事件成立。
**中断服务函数必须极短** —— 这是嵌入式的基本纪律。

### 4.4 ⚠️ 三条保护层（缺一不可）

原题要求限位"**切断电机供电**""**确保门体不超程**"。**光靠中断做不到"确保"** ——
MCU 跑飞、中断被屏蔽、代码死锁时，电机照样冲到底把机构顶坏。

| 层 | 手段 | 防的是什么 |
|---|---|---|
| **1. 硬件** | 限位开关 **NC 触点串联在 5 V → L9110S 的 VM（电机供电）路径上** | MCU 完全失效时仍然断电。**这是"确保"的唯一实现** |
| **2. 中断** | EXTI，抢占优先级 **0** | 正常情况下的快速响应与状态记录 |
| **3. 软件** | 电机运行超时兜底（5 s）+ 状态机非法转移自锁 | 中断漏触发、机械卡死 |

**只做第 2 层是这类设计最常见的失分点。** 答辩时大概率会被问"MCU 死机了怎么办"。

## 5. 数据存储设计（AT24C32 EEPROM）

### 5.1 为什么用外部 EEPROM，而不是 STM32 内部 Flash

| 方案 | 擦写寿命 | 评价 |
|---|---|---|
| STM32F103 内部 Flash | **约 1 万次** | ❌ 门禁每天几十次记录，**一两年就写坏** |
| **AT24C32（外部 I2C）** | **100 万次** | ✅ 够用十几年，且不占总线资源冲突 |

结论：**用外部 EEPROM**。AT24C32 = 32 kbit = **4 KB**，I2C 地址 `0x50`（7 位），
**直接挂在现有 I2C 总线上，零新增引脚**。

### 5.2 存储布局

```
偏移        内容
0x0000      ┌─ 头部 (32 B) ─────────────────┐
            │ magic      "ADRM" (4B)        │  用于识别是否已初始化
            │ version    0x01   (2B)        │
            │ count      已存记录数 (2B)     │
            │ wr_index   下一个写入槽 (2B)   │
            │ delay_ms   自动关门延时 (2B)   │  可被串口修改后持久化
            │ boot_count 开机次数 (4B)       │
            │ reserved   (16B)              │
            └───────────────────────────────┘
0x0020      ┌─ 记录区 252 条 × 16 B = 4032 B ┐
            │ 循环缓冲，写满后覆盖最旧记录    │
            └───────────────────────────────┘
```

### 5.3 单条记录格式（16 字节，紧凑二进制）

| 偏移 | 字段 | 类型 | 说明 |
|---|---|---|---|
| 0 | `seq` | uint16 | 记录序号（掉电不重置，用于排序） |
| 2 | `timestamp_ms` | uint32 | **开机相对毫秒数**（本方案的时间来源） |
| 6 | `boot_id` | uint16 | 本次开机编号（区分不同上电周期） |
| 8 | `event` | uint8 | 事件类型（见下表） |
| 9 | `state` | uint8 | 触发后的门体状态 |
| 10 | `mode` | uint8 | 工作模式（自动/手动） |
| 11 | `duration_ms` | uint16 | 本次开/关门耗时（诊断机械老化） |
| 13 | `reserved` | 3 | 对齐 |

**事件类型编码**：

| 值 | 事件 | 值 | 事件 |
|---|---|---|---|
| 0x01 | 进门（门外红外触发） | 0x07 | 关门到位 |
| 0x02 | 出门（门内红外触发） | 0x08 | 急停 |
| 0x03 | 开始开门 | 0x09 | 开门超时故障 |
| 0x04 | 开始关门 | 0x0A | 关门超时故障 |
| 0x05 | 开门到位 | 0x0B | 模式切换 |
| 0x06 | 关门途中反转 | 0x0C | 参数修改（延时/模式） |

### 5.4 ⚠️ 两个关键实现约束

**约束 1：绝对不能在中断里写 EEPROM。**

一次 16 字节写入 = I2C 启动 + 地址 + 数据 + **5 ms 写周期等待**。
如果在中断里做，会阻塞所有低优先级中断，导致限位响应延迟 → **撞门**。

**做法**：事件发生 → 只往 RAM 队列里塞一条 → **主循环**批量落盘
（攒够 8 条或每 500 ms 一批）。掉电最多丢最后 500 ms 的记录，可接受。

> 若日后要"一条不丢"，需加掉电检测（PVD）+ 大电容供电完成最后一次写。
> 本阶段不做。

**约束 2：I2C 总线必须在"重置地址指针"后才安全复用。**

AT24C32 的读操作依赖一个**内部地址指针**。如果一次读写被中断打断，
指针会停在中间状态，下一次访问就会从错误地址开始 —— 记录错乱且难查。

本设计用**软件 I2C**（复用现有 `MyI2C`），先做两处加固：

1. **每次事务前加 `Stop` 复位时序**，强制从机状态机回到已知状态
2. **更新 `MyI2C` 为"每次操作重置时钟线"**，避免总线卡死后无人恢复

## 6. 串口通信协议

PC 与（未来的）蓝牙**共用同一套协议**，只是因为 USART1/USART2 分开所以互不干扰。
**全部为 ASCII 行文本、以 `\r\n` 结尾** —— 好处是任何串口助手/蓝牙终端
都能直接调试，不需要写上位机。

### 6.1 主动上报（设备 → PC）

开机时：

```
=== AUTO DOOR SYSTEM v1.0 ===
MCU: STM32F103C8T6  CLK: 72MHz
BOOT #37  SELF-TEST: LCD=OK EEPROM=OK LIMIT=OK
MODE: AUTO  DELAY: 5000ms
```

运行中每发生一个事件，立即上报一行：

```
[00:01:23.450] BOOT#37 EVT=ENTER_IN   S=OPENING  M=AUTO  DUR=--
[00:01:25.010] BOOT#37 EVT=DOOR_OPEN  S=OPEN     M=AUTO  DUR=1560ms
[00:01:30.052] BOOT#37 EVT=DOOR_CLOSE S=IDLE     M=AUTO  DUR=1502ms
[00:02:11.330] BOOT#37 ERR=OPEN_TIMEOUT S=STOPPED M=AUTO
```

`[时间]` 是**开机相对时间**，PC 端收到后自行换算成绝对时间（本方案的时间策略）。

### 6.2 上位机指令（PC → 设备）

| 指令 | 功能 | 应答（**与代码逐字一致**） |
|---|---|---|
| `STATUS?` | 查询当前状态 | `OK STATUS RUN=1 MODE=AUTO DOOR=IDLE FAULT=NONE DELAY=5000ms CNT=37 TOTAL=128 LIM=0/1 I2C=ok`；有丢弃事件时在 `TOTAL` 后追加 `DROPPED=n` |
| `LOG?` | 查询最近 N 条记录（默认 10） | 首行 `OK LOG <n> of <count>`，逐行 `REC`，末尾 `OK LOG END`；无记录时 `OK LOG EMPTY` |
| `LOG?<n>` | 查询最近 n 条 | 同上 |
| `LOG?ALL` | 查询全部记录 | 同上 |
| `LOG?CLEAR` | 清空日志（与 `DEFAULTS` 分开，避免误清历史） | `OK LOG CLEARED` / `ERR EEPROM` |
| `DELAY=<ms>` | 设置自动关门延时（1000–30000） | `OK DELAY=8000`；写 EEPROM 失败时改回 `OK DELAY=8000 (NOT PERSISTED - eeprom write failed)` |
| `MODE=AUTO` | 切自动模式 | `OK MODE=AUTO`（同上，失败时带 `(NOT PERSISTED ...)`） |
| `MODE=MANUAL` | 切手动模式 | `OK MODE=MANUAL`（同上） |
| `DOOR=OPEN` | 手动开门。系统未使能或已在开门/已开到位时不动作 | `OK DOOR OPENING` / `ERR BUSY (state=... run=...)` |
| `DOOR=CLOSE` | 手动关门。**检测到有人时拒绝启动** | `OK DOOR CLOSING` / `ERR BUSY (state=... run=...)` / `ERR OCCUPIED (person detected in doorway)` |
| `STOP` | 紧急停止（锁存，需 `RESET` 清除） | `OK EMERGENCY STOP` |
| `RESET` | **清除故障锁存**并重新读取门位。**不是恢复出厂设置** | `OK RESET (fault latch cleared)` |
| `DEFAULTS` | 恢复出厂设置：延时回 5000 ms、模式回 AUTO（**不清日志**） | `OK DEFAULTS delay=5000ms mode=AUTO (log kept)` |
| `HELP` | 列出指令 | `OK HELP ...` |

> **这张表的"应答"列是照着 `App/Cmd.c` 里的 `UART_Printf` 抄的，不是凭记忆写的。**
> 细节很重要：`DOOR=OPEN` 回的是 `OK DOOR OPENING` 而不是裸 `OK`，`RESET` 回的是
> `OK RESET (fault latch cleared)` —— 上位机如果按裸 `OK` 做前缀匹配是对的，
> 但若按整行相等判断就会全部误判失败。

> **关于 `RESET` 的命名**：本节初稿写的是"恢复出厂设置"，但代码实现的是清除故障锁存 ——
> 两者是完全不同的操作，且前者会破坏配置。已按**代码实际语义**修正文档，并把
> "恢复出厂设置"独立为 `DEFAULTS` 指令。原因是：把破坏性操作藏在一个看起来无害的
> 名字后面是危险的，而上位机误发 `RESET` 清掉用户配置也是真实的损失。
>
> 同理，清日志用独立的 `LOG?CLEAR`，不与恢复默认值合并。

**错误应答**：`ERR UNKNOWN_CMD` / `ERR BAD_ARG` / `ERR BUSY`

**为什么用行文本而不是二进制**：本项目是"PC 端存储与管理"，
用文本协议**调试成本几乎为零**（串口助手直接发指令），
且未来加蓝牙时手机 APP 可以用现成的"蓝牙串口助手"顶替，**不必自己写 APP**。

> 预留：`LOG?` 的结果同时显示在 OLED 上，满足"查询结果在 OLED 显示"的要求。

### ⚠️ 现有 MyI2C 的健壮性缺口（需加固）

现有实现的基本时序是**正确的**（开漏输出不切方向、每次事务有 Start/Stop、
超时保护有界不会死循环）。但在"OLED + EEPROM 共用一条总线"的场景下，
有三个**健壮性缺口**会在偶发情况下演变成难以复现的故障：

| # | 缺口 | 后果 |
|---|---|---|
| 1 | **中途失败不发 Stop**：`MyI2C_Start()` 后若某字节 NACK，调用方直接 `MyI2C_Stop()` 结束。但若超时路径在 `ReceiveByte` 内部提前 `return`，**SCL 会停在低电平**，从机的状态机停在进行中 | 从机等待更多时钟，占用总线；下次通信可能整体错位 |
| 2 | **无总线恢复机制**：若从机因噪声把 SDA 拉死（很常见于电机附近的强干扰环境），本实现**无法恢复**，只能靠重新上电 | 门禁"死机"，必须断电 |
| 3 | **AT24C32 地址指针无保护**：AT24C32 的读依赖内部地址指针，且**写周期内（约 5 ms）不响应总线**。若在写周期里发起下一次访问，会得到 NACK 或错位数据 | 记录错乱，且极难定位 |

**加固方案**（改动约 120 行，是 EEPROM 可靠性的地基）：

1. **每个底层操作保证出口状态确定** —— 任何 `return` 路径都让 SDA 释放、SCL 拉低
2. **增加 `MyI2C_BusRecover()`** —— 检测到 SDA 被拉死时，手动发 9 个时钟脉冲
   + 一个 Stop 序列，强制从机复位状态机（I2C 标准的"总线清除"手法）
3. **增加 ACK 轮询等待** —— 写 EEPROM 后轮询"acknowledge polling"，
   等器件真正写完再继续，而不是盲等固定 5 ms（更快也更可靠）

> 这条加固**必须在写 EEPROM 之前完成**。否则会出现"OLED 正常但 EEPROM 偶发读写错"
> 这种极难复现的问题。

### 9.2 Proteus 仿真

**必须提前知道的限制**：

| 模块 | Proteus 情况 | 应对 |
|---|---|---|
| STM32F103C8 | ✅ 8.6+ 有模型 | 直接用 |
| **OLED12864 I2C** | ✅ **使用 Proteus OLED12864 I2C 模型** | 真机和仿真均使用 SSD1306-compatible OLED 后端；仿真仅将 EEPROM 替换为 stub |
| 红外传感器（按键模拟） | ❌ 无模型（本就用按键） | 直接用**按键**触发，与真机接口一致 |
| L9110S | ⚠️ 模型可能不稳 | 用 **L293D** 替代仿真（逻辑等价，都是 H 桥） |
| AT24C32 | ✅ 有 `24C32` 模型 | 直接用 |
| HC-05 蓝牙 | ❌ 无可用模型 | 本阶段不做 |

**由此引出一个必须的设计要求**：显示层要做**抽象封装**。

```c
/* app_display.h —— 业务层只调用这一层，不直接调 OLED_xxx */
void Disp_Init(void);
void Disp_ShowMain(DoorState_t s, uint8_t mode, uint32_t holdMs);
void Disp_ShowLog(uint16_t index, const LogEntry_t *e);
void Disp_ShowMsg(const char *msg);
```

真机和仿真均调用 `OLED_*`，**业务代码一行不改**；仿真固件仅使用 `EEPROM_Stub.c`。
如果不做这层抽象，等到仿真阶段才发现要改显示，返工量会很大。

**建议的仿真策略**：**不要试图仿真整个闭环系统**（耗时且 Proteus 对电机/传感器
建模失真）。改为**分模块验证**：

1. GPIO + 按键中断 → 观察 LED/蜂鸣器响应
2. **软件 PWM** → 用虚拟示波器看 1 kHz 波形、占空比随软启动斜坡变化
3. 串口 → 用 **Virtual Terminal** 收发指令，验证协议
4. EEPROM → 写入后断电重启，验证数据保持
5. 限位逻辑 → 手动触发开关，验证状态机转移

最后在真机上做整机联调。**这是性价比最高的路径。**

### 12.5 新增工具：原理图与固件的一致性校验

**问题**：引脚信息存在两处 —— `Core/main.h` 与原理图说明文档 —— 而重复的信息必然漂移。
硬件固件不一致是这类项目里最贵的一类 bug：板子按 PB10 布线、固件驱动 PB6，
不查到深夜用表笔量不出来。

**做法**：`tools/gen-hardware.py` 把 `Core/main.h` 当作**机器可读的唯一真相**，
解析出全部端口/引脚宏，与脚本内的网络表交叉校验，并生成三份产物：

| 产物 | 内容 |
|---|---|
| `generated/mcu-pinout.csv` | 逐引脚：网络名、固件宏、功能、适用构建 |
| `generated/netlist.txt` | 按网络分组的连接表 |
| `generated/bom.csv` | 元件清单 |

> **产物放在 `generated/` 而不是 `hardware/`**：Windows 文件系统不区分大小写，
> 而驱动源码目录叫 `Hardware/`，两者是**同一个目录** —— 早期版本把三个生成文件
> 直接写进了驱动源码树里。生成物混进手写源码中，就看不出哪些是源、哪些是派生物了。
> 换个名字彻底消除歧义，比依赖大小写区分可靠。

**它检查四件事**：

1. 每个 `_PIN` 宏都能找到一个对应的 `_PORT`（支持共享端口与 `_GPIO_PORT` 这类变体）
2. 每个固件引脚**恰好**被一个网络占用（同一物理引脚有两个网络，仅当它们属于
  互斥的构建时才允许；当前 OLED I2C 在真机和仿真中使用同一组 PB10/PB11）
3. 每个网络引用的宏**确实存在**（宏改名不会静默孤立一个网络）
4. 除了显式声明的 `RESERVED_PINS`，**没有宏定义了却没接进原理图**

> **这个工具第一次运行就查出了第 23、24 项。** 它不是事后补的文档，是能失败、
> 也确实失败过的检查 —— 第 7 轮里它先报 `UART_TX/RX` 匹配不上端口，
> 又逼出了 LED 归属那处我自己写反的错误。

### 12.6 关于 Flash 占用的说明（诚实记录）

**38.70 % 已超出第 8 节预算的约 34 %，余量优势消失，原因是可量化的：**

| 来源 | 估算 | 说明 |
|---|---|---|
| 中文字库 `OLED_CF16x16` | 约 1.5 KB | 江协字库，本工程三屏界面**未使用中文**，可直接删除 |
| 软件双精度浮点库 | 约 2 KB | 仅 `OLED_DrawArc`/`DrawEllipse` 的 mid-point 算法需要；本工程**未画椭圆弧** |
| `vsnprintf`（控制台） | 约 1.5 KB | `UART_Printf` 仍在用，是唯一保留的 stdio 使用者 |

> 这三项都是**为上层可选功能保留**的，而非门控逻辑必需。
> 若目标是压缩体积，按上表顺序删除即可回收约 5 KB，且不影响任何门控功能。
> 本轮**没有删除**：中文与绘图函数是江协驱动的公开能力，删掉会让使用者以为驱动有缺陷；
> 判断依据是门控功能优先级更高，而 64 KB 目前仍够用。

**已验证的收益**：`vsprintf` 与 `__aeabi_ddiv` 已从链接中消失（用 `AutoDoor.map`
的 "Archive member included" 段核对），`malloc`/`realloc`/`atexit` 一系仍由
`vsnprintf` 拉入。

### 12.10 存储层专项修复（round 10）

对 `App/Log.c` 做了一次专项通读（用户要求"先修存储日志问题"），查出 **6 项缺陷**，
全部修复。这一层此前的测试覆盖最薄：只在编译期被检查过，没有任何路径被执行过。

| # | 问题 | 性质 |
|---|---|---|
| **S1** | `rebuild_from_records()` 里有一行 `s_hdr.totalEvents = 0U`，而 `Log_Init()` 是**先**从头部读出累计计数、**再**调用它的，随后第 342 行的 `header_write()` 又把 0 写回 EEPROM | **确定性数据丢失**：`TOTAL=` 每次上电归零，§12.3 第 8 项专门引入的 64 位累计计数器等于从未生效。它不会报错、不会崩溃，只是那个数字永远是 0 —— 这类 bug 只有把 `Log_Init()` 的语句顺序读一遍才能发现 |
| **S2** | `Log_Flush()` 中途写失败时直接 `return`，`s_pendingCount` 不变但 `s_hdr.wrIndex` 已经前移。下次重试从 `i = 0` 开始 → **已成功的记录被写进新的槽位** | 环里出现重复条目，且 `totalEvents` 被重复累加（重试多少条就多算多少条）。触发条件恰好是"EEPROM 被电机噪声干扰"这个现实场景 |
| **S3** | `Log_Tick1ms()` 在 **SysTick 上下文里直接调用 `Log_Flush()`** | 一次批量落盘 ≈ 45 ms 的阻塞 I2C 在**中断里**执行。三个后果：① UART（抢占优先级 1）被阻塞 45 ms，115200 下一字节约 87 µs，**接收字符成百地丢**；② 主循环中正在进行的 I2C 事务被 SysTick 打断，两条事务在**同一条总线上交错** → 数据写错地址；③ 主循环的 flush 与 SysTick 的 flush **重入**同一个函数。此外它直接违反了 `Log_Add()` 自己文档里写的"never blocks and never touches the EEPROM" |
| **S4** | `LOG?` 从不先落盘（`Log.h` 第 87 行一直写着 "used before reporting counts"，但从没有实现） | 最近 ≤500 ms 的事件查不到。用户看着门动了、立刻查日志，日志说"没这回事" |
| **S5** | `Log_Clear()` 物理擦写全部 252 槽 | ① 阻塞主循环 **1.3 s**（252 次 × ~5 ms），期间 `Door_Update()` 完全不跑 —— 包括那条"电平触发的反转安全网"，人站进门里也不会被看见。原注释说"不在限位路径上，所以不会延误安全响应"，**这个推理是错的**：限位 ISR 不是唯一的安全层；② 每次清空消耗 252 次 EEPROM 写寿命。另外中途失败时"保留头部"的注释与事实相反：记录已经被擦掉一部分，头部却说它们还在 |
| **S6** | `Log_Init()` 无条件用 `s_hdr.seqNext` 重置序号计数器 | 落盘顺序是"先写记录、后写头部"，**掉电发生在两者之间**就会留下头部不知道的记录。重启后序号从头部的旧值继续 → **序号重复**。而"谁最新"正是靠序号比较判断的，重复序号会让环的顺序变得含糊 |

#### S5/S6 的修法（值得单独说明，因为改的是设计而不是补丁）

**S5 用代际号（generation）取代物理擦除。** 每条记录带一个头部的 generation 副本，
只有两者相等才算是有效记录。于是"清空"变成：generation + 1、count/wrIndex 归零、
写一次头部。头部正好 32 字节 = AT24C32 的**一整页**，所以这是一次**原子页写**：

- 掉电发生在清空过程中 → generation 没变 → 要么"清掉了"要么"没清掉"，**不存在擦了一半的环**
- 清空耗时从 1.3 s 降到 ~5 ms，安全网不再被撕开
- EEPROM 写寿命从每次清空 252 次降到 1 次

16 位计数器在 65535 次清空后会重复，那时会把老记录"复活"，所以在回绕的那一次做一次物理擦除
（唯一保留的慢路径，65535 次里发生一次）。**这个回绕边界不是我事后想到的，是把
"什么情况下旧记录会重新变有效"这个问题问到底问出来的。**

顺着同一个问题再问一步，发现**升级走的是同一条死路**：版本不匹配时如果把代际号重置为 1，
那么"上次升级前刚好处于代际 1"的那批记录会立刻重新可见。所以版本迁移路径改为
**代际号 = 旧值 + 1**（**单调递增**），只有真的回绕到 0 时才做物理擦除。
把"有效性"建立在一个只增不减的数上，比建立在一个每次重置的常量上要难错得多。

**S6 改为取"头部值"与"扫描到的最新序号"中较新的那个**，而不是无条件相信头部。
这同时修掉了掉电丢头部和头部页写失败两种情况。

#### S3 的修法：把 I2C 从事务上下文搬出去

`Log_Tick1ms()` 现在只置一个 `s_flushRequest` 标志，新增的 `Log_Process()`
在主循环里消费它并做真正的落盘。`Log_Add()` 也从"同步 flush"改为"置请求位"，
于是它终于符合自己文档里的承诺。

> 这是本轮唯一一处**架构性**修改：中断只做"记录请求"，所有可能阻塞的操作都回到主循环。
> 我之前把"1 ms 定时器驱动一切"当成了优点，但"驱动"不等于"在中断里做完" ——
> 定时器负责**发起**，主循环负责**完成**，才是对这种外设正确的分工。

#### 顺带修掉的两处退化陷阱

**其一**：`Log_Flush()` 在"记录都写成功、只有头部写失败"时会保留整个队列。若不处理，
此后 `s_pendingCount` 永远等于 8，`Log_Add()` 就会**永久丢弃所有新事件** ——
一页写不进去的 EEPROM 不应该有能力把事件记录整个关掉。现在这种情形下会把
已落盘的前缀从队列里移出（绝不能重写，那会造成重复），队列随即恢复可用。

**其二（这是 S3 的修法自己带出来的新问题 —— 改完后重新追一遍重试路径才发现的）**：
把 flush 改成"队列满就请求"之后，如果 EEPROM 停止应答，队列会**一直是满的**，
于是 `Log_Tick1ms()` 每 1 ms 请求一次、主循环每轮都发起一次写入尝试，
而每次失败的尝试要耗掉一整个 `EEPROM_WRITE_TIMEOUT_MS`（20 ms）的轮询。
结果是主循环被一条不应答的总线拖住，**门的状态机被饿死**。
现在加了 `s_flushFailed` 退避标志：上次失败过就禁用"队列满立即刷"的快路径，
重试改由 500 ms 定时器节流。

> 教训：**架构改动会引入新问题，改完必须把新路径自己也追一遍。**
> 这个 bug 不在原始清单里，是修复动作的副产物 —— 而它比原始问题更严重
> （原文只是日志慢，新问题是状态机被拖慢）。

#### 这次修复暴露的方法问题

S1 和 S2 都不是并发问题、不是时序问题，而是**把 `App/Log.c` 从头到尾按调用顺序读一遍
就能发现的问题**。我此前对这一层的检查方式是"它编译通过、`Log.h` 的注释说得通"，
而注释恰恰是这个文件里最不可信的部分——S4 的注释写着"used before reporting counts"
却从未实现，S5 的注释给出了一个错误的推理，S6 的问题被"记录才是真相"这句正确的
设计原则掩盖了（原则对，但没有应用到序号上）。

> 教训：**注释描述意图，代码描述行为，两者不一致时以代码为准，并且要主动去找不一致。**
> 本轮 6 项里，有 3 项（S4/S5/S6）的根因都是"注释里的正确原则没有被落实到代码"。

#### 12.10.2 新增检查工具：`tools/check-log-layout.py`

EEPROM 格式**同时写在三个地方**，而三者都可能各自漂移：`Log.c` 顶部的 ASCII 布局注释、
`HDR_OFF_*` 偏移宏、以及 `header_write()` / `record_write()` / `record_read()` 里真正的
`put16/put32/buf[]` 调用。这类漂移**不会产生任何编译警告**，在 hex dump 里也看不出来，
除非你已经怀疑有问题。而且头部正好是 AT24C32 的**一整页**（32 字节），字段一旦越界就会
落进第一条记录的槽位。

这个脚本交叉校验这三处，并额外检查：

1. 每个字段偏移都在界内（头部 < 32，记录 < 16）
2. 同一条写路径内**没有两个字段覆盖同一字节**
3. 注释里声明的每个字段**确实被写**，且偏移与宏一致
4. **成员名与偏移的配对正确** —— 写入端与读取端都要与脚本内的规范对照表一致。
   这是 C 语言**做不到**的检查：`record_write()` 里的偏移是字面量，
   把 `buf[8]` 写成 `e->doorState`、`buf[9]` 写成 `e->event` 会**编译干净、两个
   `_Static_assert` 全过**，而每条记录的事件与门态字节互换。头部同理
   （把 `s_hdr.count` 写进 `wrIndex` 槽）
5. 记录里**写了没读**（数据静默丢失）或**读了没写**
6. 记录区不与 EEPROM 自检的末尾 scratch 区重叠

> **它对自己也做了防呆**：如果正则没匹配到预期数量的字段，脚本**报错退出**而不是
> 静默通过 —— 一个"因为读不到文件所以通过"的检查比没有检查更糟。
>
> 而且它自己也犯过两次这类错：第一版把 `put16` 的 `16` 当成**字节宽度**，报出一堆假重叠；
> 加了成员名对照表后又因为 `e->x` 与 `e.x` 记法不同而全部误报。**这正是第 5 轮那次
> 解释器失败的同一种形态** —— 检查工具本身必须被验证。我的验证方式是**往代码里注入
> 错误，确认它真的会失败**：注入字段互换、注入头部槽位写错、注入字段加宽，三种都能拦住。

#### 12.10.1 独立复核（round 10 的第 2 轮）——**它推翻了我 3 个结论**

修完 S1–S6 之后，我另外起了一个**对抗性复核**（独立 agent，任务就是来证伪我列的
10 条不变量，而不是来确认）。它报了 **7 项**，我逐条核实，**7 项全部成立**，
其中两项是我**刚写下的修复本身带出来的**：

| # | 问题 | 我原来的错误结论 |
|---|---|---|
| **R1** | **代际号仍可能撞上环里已有的戳记。** `版本不匹配时用 头部 generation + 1` 依赖"持久化的头部永远不会落后于记录戳记"这个前提 —— 而代码自己就会破坏它：一次 `LOG?CLEAR` 的头部页写失败后，RAM 里的 generation 已经 +1，后续**记录写（其他页）成功、头部写（第 0 页）继续失败**，于是头部停在 7、记录戳记是 8；此时若发生版本升级，`7+1 = 8` **正好撞上**。blank 分支硬编码 generation 1 也有同样的问题 | "代际号单调递增所以升级不会复活旧记录"。**我只证明了单调，没证明不撞已存在的戳记** |
| **R2** | **回绕擦除失败后，`Log_Get()` 会把空白槽当成有效记录返回。** 我这次把"逐槽擦除、第一个就失败"改成了 `erase_all_slots()`，后者可能已经擦掉一部分才失败；此时 `count`/`wrIndex` 仍是旧的满环，于是每个索引都落在被擦掉的区域 → 打印出 `seq=0xFFFF event=0xFF` 的"记录" | ⬜ **这是我引入的回归**：旧代码"第一个就失败"恰好保证了环完好，我在优化时把这个性质弄丢了 |
| **R3** | **头部写失败会永久丢掉累计计数。** 循环只有在 `progress == pendingCount` 时才会走到头部写，所以 `remaining` **恒为 0** —— 我那段 `memmove` 压缩是死代码，实际行为是整个队列被清空，而 `totalEvents` 只能等下一次 flush 成功才落盘 | "把已落盘前缀移出队列就不会退化"。移出是对的，但**没有补上"头部还欠着"这件事**，所以头部会一直陈旧 |
| **R4** | **`LOG?CLEAR` 让 `TOTAL` 倒退。** 队列里已计入 `Log_TotalEvents()` 的事件被直接丢弃，`TOTAL` 从 T+1 回到 T，违背"只增不减" | 我把 `TOTAL` 定义成 lifetime 计数器，却没检查**每一条让它变化的路径** |
| **R5** | **版本迁移把配置和累计数一起清零了。** `initialise_fresh()` 重置了 delay/mode/seqNext/bootId/totalEvents，但 v1→v2 只有**记录布局**变了，这些字段的偏移完全没动、是可读的 | 我只想着"布局变了就重建"，没想到重建的范围应该只有记录区 |
| **R6** | 一次读取失败被当成"空槽"（`EEPROM_Read` 没有重试），开机扫描会静默缩短 `count` | — |
| **R7** | **`sizeof(LogEntry_t)` 是 20，不是 16**（结构体对齐填充：`seq` 后 2 字节、`mode` 后 1 字节）。`Log.h` 的注释写着 "16 bytes"，而 EEPROM 用的是显式按字节打包，所以镜像不受影响，**但注释是错的**，而且它正好会诱导后来人写出 `EEPROM_Write(addr, (uint8_t*)&e, sizeof(e))` | — |

**R7 我没有靠读代码接受，而是用编译器验的**：写了一个 `_Static_assert` 并逐个试
16/20/24，只有 20 通过 —— 顺带把这个断言留在了代码里，以后谁改字段宽度会在编译期炸出来。
我又把断言故意改错一次，确认它**真的会失败**（一个不会失败的检查等于没有检查）。

**复核同时确认了 4 条我关心的性质成立**（无越界写、无重复记录、中断不做 I2C、
偏移都在界内且注释/宏/读写调用三方一致），并指出 `s_flushFailed` 是对的。

> **这一轮最重要的收获不是那 7 个 bug，而是"谁来验"这件事。**
>
> 我自己修完 S1–S6 之后的判断是"已修完、已编译、推理过一遍"。一个专门被要求
> **证伪**的独立复核，在同一份代码上找到了 7 项 —— 其中 2 项（R1/R2）是我修复
> 动作的**直接副产物**。我自己的"再审一遍"没有发现它们，因为我审的是**我想验证的
> 那几条**；复核审的是**我没说出口的前提**（"头部不会落后于记录"）。
>
> 另外：R3 我写的 `memmove` 是段**永远执行不到实质逻辑的死代码**，而我当时认为它是

| # | 问题 | 性质 |
|---|---|---|
| **F-A** | **两个 `_Static_assert` 里有一个是反的，而且两个都抓不到真正的问题。** `sizeof(LogEntry_t) != LOG_ENTRY_SIZE` 在结构体变成 12/28 字节时**通过**，只在"结构体刚好等于 16"这个安全情形下才报错。另一个是**字面量求和**（`2+4+2+1+1+1+2+2+1`），**根本不读结构体**，改任何字段类型它都无动于衷。而我的注释写着"这些断言在字段宽度变化时会让编译失败" —— **注释在撒谎** | 我为了"防止注释与代码不一致"加的东西，**自己就是注释与代码不一致** |
| **F-B** | **`Log_Clear()` 把驱动错误码直接透传，与我自己定义的含义撞车。** 尾部是 `return rc;`，而 `rc` 是 `MYI2C` 码，`MYI2C_ERR_TIMEOUT == 2` —— 正好是 `Log.h`/`Cmd.c` 里"回绕擦除未完成"的 2。于是一次**普通的头部写超时**会报 `ERR EEPROM (clear incomplete, 0 records remain)`，而实际清空在 RAM 里成功了、根本没触发擦除 | 上一轮修 R2 时引入的 |
| **F-C** | **R1 的修法仍然有洞。** `scan_max_stamp()` 扫的是**能读到的**槽位：一个 3 次读取全失败的槽位会**藏起它的戳记**，算出的 generation 仍可能正好落在它身上 | **我用"扫描"去解决"有东西扫描不到"的问题** —— 逻辑上不可能成立 |

#### F-C 的修法：不是打补丁，而是把问题删掉

F-C 指出的洞没法靠更聪明的扫描补上，因为**扫描天然不完整**。所以我不再计算任何代际号：
**在 fresh/迁移路径上无条件把记录区擦空**，然后直接用 `LOG_GENERATION_INIT`。

擦空之后每个槽位都读回 `0xFF`，`rebuild_from_records()` 的"空槽"判断与代际号**无关**，
于是**根本不需要对未知数据做任何算术**。代价是 252 次页写（~1.3 s），而这条路径只在
头部不可读或记录布局变更时走 —— **一台设备一次，或每次固件版本升级一次，而且发生在
主循环还没开始跑的时候**。用一次性的 1.3 s 换掉一整类"读不到的槽位"的推理，很划算。

`scan_max_stamp()` 整个删掉了，`initialise_fresh()` 少一个参数、少三个分支。

> 本轮最值得记的一件事：**面对"我的扫描可能漏掉东西"这类反驳，正确的回应通常不是
> 把扫描做得更全，而是换一个不需要扫描的设计。** R1 与 F-C 是同一问题的两次尝试，
> 第一次（头部 +1）和第二次（扫描取最大）都错在**想要推断出**一个安全的值，
> 而正确做法是**制造出**一个安全的状态（空环）。

#### F-A 的修法：把注释改成真话，把检查放到能检查的地方

- 求和改成 `sizeof(((LogEntry_t *)0)->field)`，**真的读结构体**了。我把 `durationMs`
  从 `uint16_t` 改成 `uint32_t` 验过，断言确实拦住了（旧的字面量版本抓不到）。
- 反的那个断言改成 `sizeof(LogEntry_t) > LOG_ENTRY_SIZE`。
- **注释重写成逐条列出"覆盖什么、不覆盖什么"**，并明确指出：`record_write/record_read`
  里的字节偏移是字面量，**C 里没有任何构造能检查它们**，那个守卫在
  `tools/check-log-layout.py`。

复核者举的触发例子（交换结构体成员声明顺序）**其实不会破坏线格式** ——
`record_write` 按成员名读，不依赖结构体偏移。但它指出的**缺口是真的**：
把 `record_write` 的 `buf[8]` 写成 `e->doorState`、`buf[9]` 写成 `e->event`，
两个断言都过、编译干净、每条记录的事件与门态字节互换。所以给检查器加了
**"成员名 ↔ 偏移"对照表**，写入端与读取端都要与它一致。我注入了两种错法验证它真的会失败
（写入端换名、头部把 count 写进 wrIndex 槽）—— 后者本来也抓不到，现在能了。

### 12.11 高风险问题评审（round 11）

由使用者提出的"除了电机还有哪些高风险问题"，我逐条核实后**确认 4 项**，本轮修复 2 项，
2 项列入已知风险。**没有任何一项是电机问题。**

#### E1（高，已修）限位与传感器抢 EXTI0/EXTI1 —— 限位的中断路径**根本不存在**

使用者的描述是对的，但比"更可能连到传感器"更严重：**是确定性的**。

| 位置 | 做了什么 |
|---|---|
| `main.h:12-17` | 写明规则："八个引脚**必须**落在八个不同编号上" |
| `main.h` 原第 162/186 行 | 却给出 PA0/PA1 与 PB0/PB1 —— **八个引脚只占六个编号** |
| `Limit.c:66-67` | `Exti_ConfigPin(PA0/PA1, 优先级 0)` |
| `main.c:231,233` | `Limit_Init()` 先，`Sensor_Init()` 后（顺序固定） |
| `Sensor.c:33-34` | `Exti_ConfigPin(PB0/PB1, 优先级 2)` —— **覆盖** AFIO_EXTICR 与 NVIC 优先级 |
| 所有调用点 | `(void)Exti_ConfigPin(...)`，**没有一个检查返回值** |

后果：PA0/PA1 **不产生任何中断**；`EXTI0/1_IRQHandler` 里的 `Motor_EmergencyStop()`
是**不可达代码**；抢占优先级 0 上**没有任何中断**（文档里那条阶梯实际是 1/2/3）；
ISR 靠读**限位引脚**判断来源，而中断来自**传感器引脚** —— 构造上就错。

> **最刺眼的一点：规则写在 `main.h` 顶部，违反它的引脚定义在同一个文件往下 150 行处。**
> 一条只存在于注释里的规则，已经失败过一次。

**机构是安全的**（NC 硬件断电 + 每毫秒轮询 + `Door_Update` 的电平判断），但"声明的保护层"
不存在 —— 谁按文档信任"限位 ISR 立即急停"，谁就在依赖一个不存在的东西。

**修法（使用者选 B：换引脚）**

- 红外改 **PB12/PB13**（EXTI12/13，共用 `EXTI15_10` 向量，同一优先级）。
  拒绝的替代方案与理由写在 `main.h`：`PA2/PA3` 是 USART2（蓝牙预留）、
  `PB2` 是 BOOT1（板上下拉）、`PB9` 与按键共用 `EXTI9_5` 向量。
- **两处会失败的检查**取代注释：
  1. `main.h` 的**编译期断言** —— 用"八个引脚的按位和 == 按位或"判断编号是否互异，
     重复即数组长度为负、编译失败。**我故意把传感器改回 PB0 验证过它真的会失败。**
  2. `Exti_ConfigPin()` **拒绝**把已有线改映射到别的端口，并计数；`main()` 在串口就绪后
     打印冲突数（输入模块初始化早于串口，所以只能延后报）。
- 两个 ISR 简化为"只处理限位"，删掉那段构造上就错的引脚分支。

**连带发现（由 `tools/gen-hardware.py` 当场查出，我自己没想到）**：
`PB12/PB13` 在仿真和真机中都作为门内外 KEY 模拟传感器输入，OLED12864 I2C 共用
真机的 `PB10/PB11` 总线，因此两套构建的引脚含义保持一致。
附带好处是仿真不再碰 PB10/PB11，那条"I2C/LCD 复用"特例**从工具和文档里一并删掉了**。

#### E2（高，已修）`LOG?ALL` 会堵住控制回路约 **2 秒**

- `UART_SendByte` 原来是**纯 TXE 忙等、没有发送缓冲** → 115200 下一字节 86.8 µs
- 一条 `REC` 行 ≈ 92 字符 ≈ **8 ms**；满环 252 条 ≈ **2.0 秒**
- 这 2 秒里 `Door_Update()` 不跑（电平反转安全网失效）、`poll_inputs()` 不跑
  （**KEY4 急停失效**）、串口输入也不解析（**命令行 `STOP` 失效**）

> **叠加 E1 的后果**：`LOG?ALL` 期间**固件里没有任何路径能停下电机**，只剩 NC 触点。

**这一条我要认。** 上一轮我刚花一整段论证"`Log_Clear()` 阻塞 1.3 s 不可接受，因为反转安全网
会失效"，然后**没有把这个论证推广到任何其他地方** —— 同一个功能里有一个更严重的同类实例
（2.0 s），我只修了我当时正在看的那个。

**修法**

- `UART` 加**发送环形缓冲**（256 B）+ TXE 中断。环空时关中断，避免空转吃 CPU；
  "先入队再开中断"的顺序保证不会丢唤醒。
- `LOG?` / `LOG?ALL` 改**分帧输出**：`cmd_log()` 只打印表头并置状态，
  `Cmd_ProcessLogDump()` 每轮主循环输出 1 条，且**只在 TX 环有余量时**才输出 ——
  于是主循环**完全不阻塞**，转储在中断里以线路速率后台进行。
- 转储期间**抑制 EEPROM 落盘**：`Log_Get()` 用相对下标寻址，落盘会推进 `wrIndex`
  使所有下标平移，列表会跳条或重复。期间事件继续在 RAM 里排队，转储结束即落盘。
- 副作用：`STOP` 现在在转储期间**能被立即处理**，这正是分帧的目的。

#### E3（中，**未修，列入已知风险**）面板刷新占住控制回路约 **140 ms**

`MYI2C_DELAY_US = 5` → 一字节 27 次 QDELAY = 135 µs ≈ 7.4 kB/s；`OLED_Update()`
每次都写**全部 8 页 × 128 = 1024 字节** → 脏标记成立时 **≈138 ms** 且发生在主循环内、
排在 `Door_Update()` 之后。倒计时每秒都在变，所以显示倒计时期间**控制回路约 4 Hz**。

> 修法是 `DispBk_Flush()` 改成每次一页（8 次 × ~17 ms），约 10 行。
> **本轮未做** —— 使用者选择只修 E1/E2。

#### E4（中，**未修，列入已知风险**）没有看门狗

全工程无 IWDG/WWDG。挂死后面板与串口彻底不响应，直到有人断电。
`HardFault_Handler` 会 `Motor_EmergencyStop()` 释放桥臂，所以**不会失控通电**，
但门就停在那儿。加 IWDG 需把 `initialise_fresh()` 的 1.3 s 擦除与 138 ms 面板刷新
算进超时，否则正常操作时会被复位。**本轮未做。**

#### 顺带修正的三处文档/工具谎言

| 位置 | 原来写的 | 实际 |
|---|---|---|
| `gen-hardware.py` 的 `FIXED_PINS` | `"shared: limit open (PA0) / sensor out (PB0)"` | 不是 shared，是**争用**，一方必输 |
| `stm32f10x_it.c` 头部 | "两个端口共用一个向量，按引脚区分来源，误判可自愈" | 按引脚猜一个**不可能来自那里**的中断来源；且限位 ISR 不可达 |
| `stm32_f10x_it.h` 原型注释 | `EXTI0_IRQHandler /* PA0 limit / PB0 sensor-out */` | 已只服务限位；另补上缺失的 `EXTI15_10_IRQHandler` 声明 |

> 三条都是同一形态：**注释描述了一个比代码更好的世界**。E1 能活过 10 轮，
> 很大程度上是因为每一处相关注释都在说"这是有意为之、且自愈"。

#### 12.11.1 台架模式：限位未接时如何让状态机仍然可测

限位还没接线时，固件读到"永远不在限位"，**每次行走都会在 `DOOR_TRAVEL_TIMEOUT_MS`
（5 s）后变成 `FAULT_OPEN_TIMEOUT` / `FAULT_CLOSE_TIMEOUT`** —— 门动 5 秒然后锁故障。
所以"把限位代码注释掉"并不能得到一个可测的门，只是把一个错误换成另一个。

改用 `-NoLimits`（`AUTODOOR_NO_LIMITS=1`）：

```
.\tools\build.ps1 -NoLimits -Flash     # 台架：位置为仿真值
.\tools\build.ps1 -Clean              # 回到真实限位（默认）
```

`Hardware/Limit.c` 在该模式下不配置引脚、不占 EXTI，而是按**电机方向 + 已走时间**
推进一个虚拟位置（0 % 全关 → 100 % 全开，全程 `DOOR_SIM_TRAVEL_MS` = 2 s，
取自 `Motor_GetDir()`，所以电机一停虚拟门也停）。

**关键在于 API 完全不变**：`Limit_IsOpen()` / `Limit_IsClosed()` 的语义一样，
于是 **`Door.c` 一行都不用改**，状态机两条 settle 路径、行程看门狗、自动关门倒计时、
反转安全网全都按真实路径运行 —— 这才是台架测试有意义的前提。

必须说清它**去掉了**什么（不是"精简版"，是"少了一层"）：

- **限位 EXTI 中断不可达** → 软件快速停机层不存在。失控时唯一挡在机构和电机之间的
  是 `+5V→VM` 上那个 NC 触点，**那是硬件**：它仍然有效，**前提是你真的接了**；
- `Limit_IsFaulted()` 恒为正常 → 限位线短路/断裂**查不出来**；
- 2 s 是猜的行程时间 → "到位"早于实际，看门狗余量也不是真的。

因此：开机横幅用 6 行警告说明、`STATUS?` 每行带 `LIMITS=SIMULATED`、
`docs/上电调试步骤.md` 有专章列出"能测 / 不能测"。**绝不烧进要驱动真门的板子。**

> 顺带一个设计上的收益：这个开关逼着我把"限位"真正当成一个**接口**来对待 ——
> 因为接口没变、只换实现，所以"状态机是否只依赖限位的语义、而不依赖它的来源"
> 这个问题被自动验证了一遍。如果当初为了台架去改 `Door.c` 里的 `#if`，
> 那答案就永远是"不知道"。
