# AutoDoor 上电调试与验证步骤

> 目的：把验证拆成**可独立判定通过/失败**的小步，每一步都有明确的预期现象。
> 不要跳过前面的步骤直接测整机 —— 状态机依赖底层的输入消抖、EEPROM 都正确。
>
> ⚠️ **本设计不安装限位开关。** 这是**出货配置**，不是临时手段：默认构建
> （`Core/main.h` 的 `AUTODOOR_NO_LIMITS` = 1）不碰 PA0/PA1、不占 EXTI，
> 门的位置由**标定行程时间** `DOOR_TRAVEL_MS`（默认 **1500 ms**；`TRAVEL=<ms>` 可
> 现场改到 600..4000 并持久化）推算，
> 行程看门狗是 `DOOR_TRAVEL_MS + DOOR_TRAVEL_MARGIN_MS` = **2700 ms**（默认值）。
> 由此带来三件事，下面每一步都按它写：
>
> - **没有 PA0/PA1 可以拨**：门的到位是**按时间**发生的；
> - **没有软件快速停机层**：电机被命令转动后，行程看门狗是唯一的超程保护；
> - **查不出限位线故障、也没有双限位冲突**：`Limit_IsFaulted()` 恒为正常。
>
> 要看限位这条链，只能用 `.\tools\build.ps1 -WithLimits` **另做一套变体**
> （仍需真的接上限位开关），见文末"可选：`-WithLimits` 变体"。

当前固件版本：`v1.0`（round 10）
实测资源占用（`-Os`）：**Flash 25360 B / 64 KB (38.7%)，RAM 4016 B / 20 KB (19.6%)**

> **这份文档里的每一行"预期串口输出"都是照着 `Core/main.c` 和 `App/Cmd.c` 的
> 实际 `UART_Printf` 改过的。** 硬件调试最怕预期文本过时：现象其实是对的，
> 你却在追一个不存在的 bug。凡是你看到的输出和这里不一致，先怀疑这份文档，
> 用代码原文核对（`Select-String -Path Core\main.c,App\Cmd.c -Pattern 'UART_'`）。

## 步骤 0：只插 Blue Pill，先确认"能烧、能连、能停"

**这一步不需要任何外设**，只需要 Blue Pill + ST-Link。它的目的是把
"工具链/接线/芯片"这一类问题和固件问题分开 —— 否则一旦后面哪步不对，
你分不清是代码错还是 SWD 没接好。

| # | 操作 | 预期 |
|---|---|---|
| a | 接 SWD：`SWDIO→PA13`、`SWCLK→PA14`、`GND→GND`、`3V3→3V3` | `st-info --probe` 报出芯片与 Flash/SRAM 容量 |
| b | `.\tools\build.ps1 -Clean -DebugBuild` | 编译 31/31 通过，产出 `build\AutoDoor.elf` |
| c | `.\tools\build.ps1 -Flash` | `st-flash` 写入 `0x08000000` 成功 |
| d | 用 GDB 连上并 `halt` | `arm-none-eabi-gdb` 能停住，`bt` 显示停在 `main` / `SysTick_Handler` |

> `-DebugBuild` 用 `-Og -g3`，变量不会被优化掉，GDB 里能正常 `print`。
> 只烧不看的时候用默认的 `-Os -g` 就行。
>
> **不要用 ST-Link 的 5 V 给电机供电**：那种小 dongle 的 5 V 直通 USB，
> 电机一启动就把 MCU 一起拉跌，你会看到莫名其妙的复位。电机必须独立 5 V 供电、
> 单点共地（前置检查 0.6）。
>
> `App_JtagDisable()` 释放的是 PB3/PB4/PA15（蜂鸣器、状态 LED），
> **只关 JTAG、不关 SWD**，所以烧录后再连也连得上。不要去改成
> `GPIO_Remap_SWJ_Disable` —— 那会把板子变成砖。

## 步骤 1：串口与自检

**接线**：USB-TTL 的 RX→PA9、TX→PA10、GND↔GND。115200 8N1。

> **没有 USB-TTL 也能验证这一步**，见本节末的"用 GDB 代替串口"。

**上电，预期串口输出**：

```
========================================
 AutoDoor  STM32F103C8T6  v1.0
========================================
I2C idle      : yes
Display       : OK
EEPROM @0xA0  : OK (4096 bytes)
Log           : boot#1, 0/252 records, delay=5000ms, mode=AUTO
*** NO LIMIT SWITCHES: position is a timed estimate (1500ms) ***
*** the travel watchdog (2700ms) is the only overrun protection ***

Position      : timed estimate, 1500ms travel (open=0 closed=1)
    state: INIT -> IDLE
Door          : IDLE (press KEY1 to enable)

AutoDoor ready. boot#1  records=0  delay=5000ms
type HELP for commands
```

> **注意这个顺序**：`I2C idle` / `Display` / `EEPROM` / `Log` 四行在最前，两条
> `***` 警告和 `Position` 在**读完 EEPROM 之后**才打（打印的是当前生效的行程时间）；
> 缩进的 `    state: INIT -> IDLE` 由状态回调插在 `Position` 与 `Door` 之间。
> 按 KEY1 使能后才会出现 `EVT … SYSTEM_START S=IDLE M=AUTO` 那类事件行。

**判定**：

| 现象 | 结论 |
|---|---|
| `I2C idle: yes` | 总线空闲正常 |
| `I2C idle: NO (bus held low)` | ⚠️ 总线被拉死 → 检查 PB10/PB11 接线、上拉、器件是否短路 |
| `Display: not found` | OLED 未应答 → 检查 PB10/PB11、地址（0x78） |
| `EEPROM: FAILED at 0xNNNN` | 记录失败地址，定位是坏块还是接线 |
| `Log: UNAVAILABLE` | EEPROM 没被识别 → 门控仍能工作，但日志与配置不持久化 |
| `EXTI : N LINE CONFLICT(S) - an input has no interrupt!` | ❌ **不该出现**：有两个输入共用了**同一个引脚编号**，后配的那个**一个中断都没有**（STM32F1 的 EXTI 线按引脚编号共用，AFIO 每条线只能选一个端口）。查 `Core/main.h` 的引脚分配与编译期断言；正常接线不会有这一行 |
| 那两行 `*** NO LIMIT SWITCHES ... ***` | ✅ **正常**（出货配置）—— 明确告诉你位置是推算值、看门狗是唯一超程保护；括号里的毫秒数是**当前生效**的行程时间与看门狗 |
| `Position: timed estimate, 1500ms travel (open=0 closed=1)` | ✅ **正确**（上电时推算位置 = 0 = 全关） |
| `Position: timed estimate, … (open=0 closed=0)` | ⚠️ 门被停在中间（上一次 `STOP` 之后的位置），不是故障 |
| `Position: limit switches, open=… closed=…` | 你烧的是 `-WithLimits` 变体 —— 那两块板子必须真的接了限位 |

> **`Position:` 这行的含义**：`open` / `closed` 不是两个开关的电平，而是**推算位置**
> 的两个端点判断（`open` = 推算到 100 %，`closed` = 推算到 0 %）。
> 因为是推算，`open=1 closed=1` 这种"双限位冲突"在默认构建里**不可能出现**，
> 所以也不会有 `LIMIT_CONFLICT` 故障上报 —— 想测那条故障只能用 `-WithLimits`。

**再上电一次**，应看到 `boot#2`，且 `records` 数量保持了上次的记录 —— 证明 EEPROM 持久化生效。

#### 用 GDB 代替串口（没有 USB-TTL 时）

ST-Link 只给 SWD，不给串口（除非你用的是 Nucleo/Discovery 那种自带 VCP 的板子）。
但 SWD 能做的事比看串口**更多**：串口只能看固件愿意打印的东西，GDB 能看**所有**变量。

```
arm-none-eabi-gdb build\AutoDoor.elf
(gdb) target extended-remote localhost:3333
(gdb) monitor reset halt
(gdb) break Door_Update
(gdb) print Door_GetState()
(gdb) print Door_GetFault()
(gdb) print Limit_IsOpen()
(gdb) print g_msTick
```

> 对 `Log.c` 里的 `static` 变量要加文件限定：`print 'Log.c'::s_hdr.count`、
> `print 'Log.c'::s_pendingCount`、`print 'Log.c'::s_flushFailed`。
> **凡是 static 变量都要这么写** —— 这正是本轮存储层修复最难自查的地方：
> 串口只暴露 `CNT=`/`TOTAL=`，而 `s_flushProgress`、`s_flushFailed`
> 这些中间状态只有调试器能直接看到。

## 步骤 2：按键与模式

| 操作 | 预期串口输出 |
|---|---|
| 按 **KEY1** | `EVT ... SYSTEM_START S=IDLE M=AUTO` + `state: ... -> IDLE` |
| 按 **KEY2** | `EVT ... MODE_CHANGE` + `OK MODE` 之类；状态行 `M=` 在 AUTO/MANUAL 间切换 |
| 再按 **KEY1** | `EVT ... SYSTEM_STOP S=STOPPED` |

**判定**：每次按键只产生**一条**事件。若一次按键出现多条，说明消抖窗口不够或
输入引脚的 EXTI 编号冲突。

## 步骤 3：位置与行程时间（**没有限位开关可拨**）

**前提**：KEY1 使能系统。

`Limit.c` 不读任何引脚：它按**电机方向 + 已走时间**推算位置（0 % = 全关 → 100 % = 全开，
全程 `DOOR_TRAVEL_MS` = 1500 ms（默认；`TRAVEL=<ms>` 可现场改，600..4000），取自 `Motor_GetDir()`，所以电机一停、推算也停）。
**"到位"因此是一个时间事件，不是一个可以按出来的开关。**

| 操作 | 预期 |
|---|---|
| 发 `DOOR=OPEN` 并计时 | 约 **1.5 s 后自己到位**：串口出现 `LIMIT open edge` + `OPEN_DONE DUR=xxxxms`，`state: OPENING -> OPEN` |
| 发 `DOOR=CLOSE` 并计时 | 约 1.5 s 后 `LIMIT close edge` + `CLOSE_DONE`，`state: CLOSING -> IDLE` |
| 行走途中发 `STOP` | 立即停；此后 `Position: … (open=0 closed=0)`（停在中间），不会自己补到端点 |
| 走完一次后看 `STATUS?` | 带 `LIMITS=TIMED` —— 提醒看日志的人"这个位置是推算出来的" |

> **`LIMIT open edge` / `LIMIT close edge` 仍然会打印**，但它们不是开关触发的边沿，
> 而是**推算到位时固件自己产生的那条边沿**（`Limit.c` 的 `s_simOpenEvent` /
> `s_simCloseEvent`，注释写着 "console still shows the edge"）。
> 看到它只能证明"固件认为到了"，**不能证明门真的到了**。

**⚠️ 超程保护：只剩行程看门狗（必须知道）**

> 默认构建**没有限位 EXTI**，所以也**没有软件快速停机层**。电机一旦被命令转动，
> 唯一会停它的是行程看门狗 `DOOR_TRAVEL_TIMEOUT_MS` = `DOOR_TRAVEL_MS` + `DOOR_TRAVEL_MARGIN_MS`
> = 1500 + 1200 = **2700 ms**（默认值；`DOOR_TRAVEL_MS` 被 `TRAVEL=<ms>` 改后，看门狗跟着当前值走）。这 1200 ms 是**看门狗对"行程超过标定值"的容忍量**：
> 状态机若在 2700 ms 内仍不收敛，固件就停机并锁故障。
> **但它并不知道门是否真的到位** —— 位置是推算的：门卡住、皮带打滑、电压跌落导致转速
> 变慢，都会照样被算成"到位"（卡的只是电机，推算照样走到头）。
> （`Core/main.h` 把这个余量描述成"允许堵转多久"；就"电机最多还会被驱动多久"这一点
> 两者是一致的 —— 区别在于堵转本身不会让推算停下，所以它**不构成卡死检测**。）
> 反过来说：**没有绝对位置、没有修正**，掉电时正在行走的门重新上电后按
> "上一次命令推断的位置"继续。

| 项 | 默认构建（不装限位） | `-WithLimits` 变体 |
|---|---|---|
| 到位判据 | 标定行程时间（默认 1500 ms，`TRAVEL=` 可改） | PA0/PA1 的限位电平 |
| 行程看门狗 | **2700 ms**（1500 + 1200 余量，默认值） | 固定 **5000 ms** |
| 软件快速停机 | **不存在** | 限位 EXTI 立即 `Motor_EmergencyStop()` |
| 限位线故障 / 双限位冲突 | **查不出来**（`Limit_IsFaulted()` 恒为正常） | `LIMIT_CONFLICT` 等可检出 |
| NC 触点串 `+5V → VM` 硬件断电 | 不装（该方案已作废，见 `接线图.md` 第 5 节） | 可选，但先读第 5 节 |

## 步骤 4：电机与调速

**注意**：130 电机必须**已装减速机构**，否则扭矩不足转不动门。

| 操作 | 预期 |
|---|---|
| 串口发 `DOOR=OPEN` | `OK DOOR OPENING`，电机**平滑加速**（约 0.4 s 斜坡）到 70% 占空比，向开门方向转 |
| 串口发 `DOOR=CLOSE` | `OK DOOR CLOSING`，电机先**停顿约 20 ms**（换向死区）再反向平滑加速 |
| 串口发 `STOP` | 立即停转 + `EVT ... ESTOP` + 长鸣 |

### 4.0 ⚠️ 第一项必须做的判定：**门必须一次走到位，中途不停**

这是整份文档里**最容易被跳过、却能抓到最严重 bug** 的一条。

| 步骤 | 操作 | 预期 |
|---|---|---|
| a | 确认门处于关闭（`Position: timed estimate … (open=0 closed=1)`） | |
| b | 发 `DOOR=OPEN`，**盯着门** | 门**持续走到底**，约 1.5 s 后 `LIMIT open edge` → `OPEN_DONE`，全程不停 |
| c | 门到 `OPEN` 后发 `DOOR=CLOSE` | 同上，反方向一次走到底 |

- ✅ 一次走到底 → 正确
- ❌ **门比 1.5 s 还慢，串口却已经报 `OPEN`** → 这是"位置是推算值"的直接表现：
  `DOOR_TRAVEL_MS` 比真门快，固件在门还没到时就认为到位并停机，**门会停在止挡之前**。
  按真门实测把标定值**改大**（宁长勿短）。
- 🔧 **改行程 + 标定，不必反复重编译**：
  1. 发 `TRAVEL=<ms>` 现场改**全行程时间**（600–4000，**运行中即时生效**，`STATUS?` 里带
     `TRAVEL=`）。默认 1500 ms 回显 `OK TRAVEL=1500ms (13 us of pulse per 20 ms frame)`；
     括号里是**两个 20 ms 舵机帧之间脉冲走多远**，低于约 10 us/帧时 SG90 会连着几帧
     忽略这点变化、门看起来一跳一跳的 —— 1000–2000 ms 是它**扫过去而不是跳过去**的窗口，
     再大就更慢更顺；
  2. 量法：发 `TRAVEL=4000`（把行程放宽到最长），发 `DOOR=OPEN`，
     用秒表量门从启动到顶住止挡的时间，再把量到的值发回去（`TRAVEL=<实测值>`）。
     **不必靠临时改源码来放宽行程** —— `TRAVEL=` 就是这个量本身；
  3. 出厂值写在源码 `DOOR_TRAVEL_MS`（默认 1500）里，重新烧录即可。
  > `TRAVEL=` **是持久化的**（写进 EEPROM，断电后仍然生效，上电时重新装载，见步骤 6 的
  > 断电验证）：它是要落在成品门上的标定值，每次上电重敲一遍没有意义。
  > SG90 分支**没有** `SPEED=<%>` —— 舵机的速度是舵机自己的，发它只会回
  > `ERR N/A - SG90 speed is fixed (use TRAVEL=<ms>)`（见步骤 6）。
- ❌ **门只动几毫米就停住、约 2.7 s 后 `FAULT: OPEN_TIMEOUT`** → 默认构建里这**不可能**
  是限位造成的（连 EXTI0/EXTI1 都没配置，`Motor_EmergencyStop()` 那条路径不存在）。
  查电机供电、`Motor_Run()` 是否被中途覆盖，以及是否有别的故障先锁存。
  **注意不要把标定值改短来"修"它** —— 标定值只决定"何时认为到位"，不决定超时。
- ❌ **报了 `*_TIMEOUT`** → 说明状态机在 `DOOR_TRAVEL_TIMEOUT_MS`（默认 2700 ms）内没有收敛。
  默认构建的到位是按时间算的（1.5 s），本该收敛；先查状态机是否被打断
  （故障闩锁、`Motor_Run()` 被覆盖、SWD 改动），而不是去调标定值。

> **为什么单列一条**：round 12 的回归是"限位的**释放边沿**把电机切了"，
> 它编译 0 warning、通过当时全部 4 个检查，而且在**不配置 EXTI 的构建里根本不会出现**。
> 所以它只在 `-WithLimits` + 真的接了限位时才暴露；那一套要走同一份判据，并检查
> `Limit_IrqHandler()` 里的 `Bit_RESET` 与 `Motor_GetDir()` 两个守卫是否还在
> （`python tools/check-limit-safety.py`）。

**判定要点**：

- **加速应该是渐进的**，不是"猛地一窜"。若瞬间全速，说明软启动斜坡没生效。
- **换向时应有短暂停顿**。若直接反转，会听到"咔"的一声且 L9110S 发热 —— 这是
  上下管直通，长期会烧模块。
- 若电机**不转但 L9110S 发热** → 电机线接错或电机电压不足。
- 若电机转但方向反了 → **对调电机的两根线**（最省事），或者改
  `Hardware/Motor/Motor.c` 里 `apply_output()` 的 `MOTOR_DIR_OPEN` / `MOTOR_DIR_CLOSE`
  两个分支里 `IA_*` / `IB_*` 的先后。注意方向编码**不在** `main.h` ——
  `main.h` 只有引脚定义，改那里不会改变转向。

**调速验证（可选，用逻辑分析仪/示波器）**：测 `PA4` 或 `PA5`。
预期看到**约 10 ms 周期**的 PWM（100 Hz），占空比在 0.4 s 内从 0% 升到 70%。
若占空比是跳变的，`Motor_Tick1ms()` 的斜坡有问题。

## 步骤 5：自动关门与倒计时

**前提**：AUTO 模式，KEY1 使能。

| 操作 | 预期 |
|---|---|
| 按模拟门外传感器键 | 门开 → `OPEN_DONE` → `OPEN`，进入 5 s 倒计时 |
| 不发任何命令等待 | 5 s 后自动 `CLOSE_START` → 关门 → `CLOSE_DONE` → `IDLE` |
| 开门后再按一次传感器键 | 倒计时**重新开始**（门保持开启） |
| 关门过程中按传感器键 | `EVT ... REVERSE` → 门**立即反转开门** → `OPEN_DONE` |

> 第 4 行是最重要的安全行为：**关门途中检出人员必须反转**。
> 若门继续关，说明 `Door_Update()` 第 3 步的传感器分支有问题。

#### 5.1 ⚠️ 电平反转验证（安全网，必做）

上面第 4 行测的是**边沿**触发的反转。还有一层**电平**触发的反转，专门防"边沿丢失"。
必须单独验证它，因为它才是失效时真正兜底的那一层。

| 步骤 | 操作 | 预期 |
|---|---|---|
| 1 | 让门处于 `OPEN` | |
| 2 | **先按住**模拟门外红外的按键不放（保持有人） | |
| 3 | 再发 `DOOR=CLOSE` 或等倒计时结束触发关门 | **门不应启动关门**，串口回 `ERR OCCUPIED (person detected in doorway)` |
| 4 | 松开按键，再发 `DOOR=CLOSE` | 这次正常 `CLOSING` |
| 5 | 门正在 `CLOSING` 时按住传感器键 | `EVT ... REVERSE` → 门立即反转 |

> 第 3 步验证的是**拒绝启动**（不会先关门再反转，避免一来一回的机构冲击）。
> 第 5 步验证的是**已经关起来之后**电平仍能救回来 —— 这才是"边沿丢失"场景的兜底。
>
> 如果第 3 步门启动了，说明第 19 项修正没生效；如果第 5 步门继续关，
> 说明第 17 项修正没生效。**这两项都是安全项，不通过不能交付。**

**验证倒计时显示**：串口每 10 s 打印一次状态行，含 `DOOR=` 与 `DELAY=`。

## 步骤 6：记录与查询

| 命令 | 预期 |
|---|---|
| `STATUS?` | `OK STATUS RUN=0 MODE=AUTO DOOR=IDLE FAULT=NONE DELAY=5000ms CNT=0 TOTAL=0 LIMITS=TIMED LIM=0/1 TRAVEL=1500ms I2C=ok`（`TOTAL` 是累计事件数，见下；`TRAVEL=` 是当前生效的行程时间；`DROPPED=n` 只在非 0 时紧跟 `TOTAL=`；`LIMITS=TIMED` 只在默认构建出现，`-WithLimits` 变体不打这个字段；**每 10 s 的周期状态行是同一格式**） |
| `LOG?` | 逐行 `REC <i> #<seq> [HH:MM:SS.mmm] boot#n EVENT S=... M=...`（`EVENT` 补空格到 18 字符，`DUR=` 只在 `OPEN_DONE`/`CLOSE_DONE` 上出现），末尾 `OK LOG END` |
| `LOG?ALL` | 列出全部记录 |
| `LOG?3` | 只列最近 3 条 |
| `LOG?CLEAR` | `OK LOG CLEARED`，之后 `STATUS?` 的 `CNT=0` |
| `DELAY=8000` | `OK DELAY=8000` |
| `DELAY=500` | `ERR RANGE 1000..30000` |
| `TRAVEL=1800` | `OK TRAVEL=1800ms (11 us of pulse per 20 ms frame)` —— 括号里是每 20 ms 舵机帧的脉冲位移；`TRAVEL=` **会写进 EEPROM**，所以下面第 3 步的断电验证也要带上它 |
| `TRAVEL=200` | `ERR RANGE 600..4000` —— 低于 600 ms 时每帧位移小于 SG90 的死区，门会一跳一跳地走，所以直接拒绝 |
| `TRAVEL=fast` | `ERR BAD_ARG` |
| `SPEED=50` | `ERR N/A - SG90 speed is fixed (use TRAVEL=<ms>)` —— 本分支是 SG90，没有可设的占空比 |
| `MODE=MANUAL` | `OK MODE=MANUAL` |
| `RESET` | `OK RESET (fault latch cleared)` —— **只清故障，不动配置与日志** |
| `DEFAULTS` | `OK DEFAULTS delay=5000ms mode=AUTO travel=1500ms (log kept)` —— 日志**保留**，行程时间也一起回到 1500 ms |
| `BOGUS` | `ERR UNKNOWN_CMD (try HELP)` |

**验证 `RESET` 与 `DEFAULTS` 的区别**（这是两个容易混淆的指令）：

1. `DELAY=9000`，产生几条记录
2. 发 `RESET` → 之后 `STATUS?` 应显示 `DELAY=9000ms` 且 `CNT` 不变（配置与日志都没动）
3. 发 `DEFAULTS` → `DELAY=5000ms`，但 `CNT` **仍然不变**（日志被刻意保留）
4. `LOG?CLEAR` → `CNT=0`（清日志是独立指令）

**断电持久化验证**：产生几条记录，发 `DELAY=8000`，再发 `TRAVEL=1800`，然后**断开电源再上电**。
预期：`boot#` 递增，`records` 与 `delay=8000ms` 都保持，`STATUS?` 仍回 `TRAVEL=1800ms`，
且开机那两行 `***` 警告打印的是 **1800ms / 3000ms**（1800 + 1200 余量）——
`TRAVEL=` 与 `DELAY=`/`MODE=` 一样会被重新装载。

- ✅ 保持 → EEPROM 日志与配置持久化正确
- ❌ 归零 → 检查 EEPROM 的页边界写入与 `Log_Init()` 的重建扫描

**`TOTAL=` 必须只增不减**（round 10 修掉的 S1）：`STATUS?` 里的 `TOTAL=m` 是**累计事件数**，
它比 `CNT` 大（`CNT` 只是环里现存的记录数）。**每次上电 `TOTAL` 都要接着上次的数继续涨**。

- ❌ 每次上电 `TOTAL` 回到 0 → `Log_Init()` 里的累计计数被 `rebuild_from_records()` 覆盖了
- `LOG?CLEAR` 之后 `CNT=0` 但 `TOTAL` **不变**（累计数是这台机器的属性，不是当前日志的属性）

**`LOG?` 必须包含刚刚发生的事件**（round 10 修掉的 S4）：让门开一次，**立刻**发 `LOG?`，
最新那条应该在里面（此前最多有 500 ms 的事件还在 RAM 队列里查不到）。

- ❌ 最新事件缺失 → `cmd_log()` 没有先落盘

**清空必须是"一次页写"而不是"擦 252 槽"**（round 10 修掉的 S5）：
发 `LOG?CLEAR`，`OK LOG CLEARED` 应当**立刻**返回（约 5 ms），而不是卡一秒多。
`LOG?CLEAR` 之后**再断电上电**，`LOG?` 仍应为空 —— 旧记录不能复活。

- ❌ 清空后卡顿约 1.3 s → 又回到物理擦除的实现
- ❌ 上电后旧记录回来了 → 代际号（generation）比对没生效

## 步骤 7：故障注入（答辩会被问的部分）

| 注入 | 预期行为 |
|---|---|
| 堵住门不让它动（电机通电但门被卡住） | 推算位置仍会**按时间**在约 1.5 s 后到达端点 → `OPEN_DONE` → `OPEN`。**"卡住"不会被识别成超时**：位置是推算值，不是测量值。这 1.5 s 里电机一直堵转 |
| 行程超时（看门狗） | 只有状态机仍停在 `OPENING`/`CLOSING`/`REVERSING` 且已超过 `DOOR_TRAVEL_TIMEOUT_MS`（默认构建 **2700 ms**，默认行程 1500 + 1200 余量）时才报 `FAULT: *_TIMEOUT` → `STOPPED`，三短鸣。**它是没有限位时唯一的超程保护**；门还在走时可用 SWD 把行程起点推早来复现：`set var 'Door.c'::s_travelStartMs = g_msTick - 4000` |
| 长按 KEY4 | 立即停机 + 长鸣 + `FAULT: ESTOP` |
| ESTOP 后发 `DOOR=OPEN` | **不动作**（故障锁存，必须先 `RESET`） |
| 断开 EEPROM | 上电打印 `Log: UNAVAILABLE`，门控**仍可工作**（降级运行） |
| 拔掉 OLED | 上电打印 `Display: not found`，其余功能正常 |

> 最后两项体现"单点故障不导致系统失效"的设计原则。
>
> **注意"拔限位线"这类注入已经不存在了** —— 没有限位线可拔。想验那一层
> （NC 触点断电 fail-safe、限位极性、限位触发的立即停机）必须用 `-WithLimits`
> 变体并真的装上限位开关，见文末。

## 已知限制（如实记录，不要隐瞒）

| 限制 | 原因 | 影响 |
|---|---|---|
| 人员检测为按键模拟 | 器件清单无可用的人员检测传感器（TCRT5000 仅约 1 cm） | 换 E18-D80NK 后接口不变 |
| **位置是推算值，不是测量值** | **不装限位开关**，位置由标定行程时间 `DOOR_TRAVEL_MS` 推算 | 卡住或空转都不会被发现；上电时一律假定门是关的；`DOOR_TRAVEL_MS` 必须按真门标定且**宁长勿短** |
| **只有一层超程保护** | 没有限位 EXTI，就没有软件快速停机层 | 电机被命令转动后，唯一会停它的是行程看门狗（默认 2700 ms）；也没有绝对位置与修正 |
| PWM 载波仅 100 Hz | 软件 PWM 受中断开销限制，20 kHz 需硬件 PWM | 电机有轻微可闻嗡声 |
| 时间为开机相对时间 | 无 RTC | PC 端换算绝对时间 |
| **关门后不"锁死"** | 电机停转即滑行（`Motor_Brake()` 是死代码，从没被调用）；130 电机无减速箱时没有保持力矩 | 需求里的"锁定位置"目前**靠减速箱自锁实现，电子部分不锁定**。面板/文档不得声称电子锁定 |
| 声音提示为定频 | 有源蜂鸣器 | 靠节奏区分事件 |

## 若某步失败的排查顺序

1. **先看串口**：固件把绝大多数故障都打成了明确文本，不要靠猜。
2. **检查 `Position:` 行与 `LIMITS=TIMED`**：默认构建里位置是推算值 ——
   它错了不代表接线错了，它"对"也不代表门真的到了。先确认自己烧的是哪个构建。
3. **检查 `I2C idle`**：总线被拉死时 OLED 和 EEPROM 都会失败。
4. **量电源**：电机启动瞬间 5 V 是否跌落？跌落会导致 MCU 复位。
5. **逻辑分析仪看 PA4/PA5**：PWM 波形能区分"软件没输出"和"驱动模块坏了"。
6. **GDB 看内部状态**：串口看不到的中间量（`'Log.c'::s_pendingCount`、
   `'Log.c'::s_flushFailed`、`'Motor.c'::s_dir`、`s_dutyNow`、`'Limit.c'::s_simPos`）
   才是排查卡住的地方。

## 默认构建去掉了什么（"台架模式"这个开关已经没有了）

以前限位没接时要靠 `-NoLimits` 才能测状态机；**现在不装限位就是默认配置**，
所以那一节描述的状态成了常态 —— 该说清的代价也成了常态。**这不是"精简版"，
这就是要出货的那一套。**

```powershell
.\tools\build.ps1 -Clean -Flash           # 默认：不装限位，位置按行程时间推算
.\tools\build.ps1 -WithLimits -Flash      # 可选：只有真的装了限位才用（见下一节）
```

**上电第一件事就是确认你烧的是哪个固件**，默认构建会打印：

```
========================================
 AutoDoor  STM32F103C8T6  v1.0
========================================
*** NO LIMIT SWITCHES: position is a timed estimate (1500ms) ***
*** the travel watchdog (2700ms) is the only overrun protection ***

...
Position      : timed estimate, 1500ms travel (open=0 closed=1)
```

`STATUS?` 每一行也会带 `LIMITS=TIMED`（因为它可能几分钟才看一次，不该只在开机时提示）。

| 去掉的 | 后果 |
|---|---|
| 限位 EXTI 中断 | **软件快速停机层不存在**。电机被命令转动后，唯一挡在机构和它之间的**只有行程看门狗**（`DOOR_TRAVEL_TIMEOUT_MS` = 默认 2700 ms，即当前行程时间 + 1200）。`+5V→VM` 上那个 NC 触点也一起取消了 —— 那条回路依赖限位开关，见 `接线图.md` 第 5 节（已作废） |
| 限位故障检测 | `Limit_IsFaulted()` 恒为"正常"，限位线短路/断裂（默认构建里根本没有限位线）**查不出来**，`LIMIT_CONFLICT` 也不会出现 |
| 实测行程时间 | 位置是**按时间推算**的，不是量出来的。`DOOR_TRAVEL_MS` 报早了门会停在止挡之前；报长了机构会多顶一会儿 —— **宁长勿短** |
| 绝对位置 | 没有位置基准、没有修正。掉电时正在行走的门，重新上电后按"上一次命令推断的位置"继续 |

### 默认构建下可以测什么

| 能测 | 不能测 |
|---|---|
| 状态机全流程（OPENING→OPEN→倒计时→CLOSING→IDLE） | 限位 HW 断电 fail-safe（回路已取消） |
| 串口全部指令、日志攒批/落盘/重启恢复 | 真实限位极性（NC/NO 接反查不出来） |

> 换句话说：**默认构建验证的是"逻辑对不对"，不是"位置这套保护对不对"。**

### A. 限位中断必须真的生效（**仅 `-WithLimits` + 真的接了限位**）

> 这一项在默认构建里没有意义：不配置 EXTI0/EXTI1，`Motor_EmergencyStop()`
> 那条路径不存在，下面这些现象都不会发生。

修复前限位**没有任何 EXTI 中断** —— 传感器把 EXTI0/EXTI1 整条抢走了，
`EXTI0/1_IRQHandler` 里的 `Motor_EmergencyStop()` 是不可达代码。

| 步骤 | 操作 | 预期 |
|---|---|---|
| a | 上电看串口有没有 `EXTI : N LINE CONFLICT(S)` | **必须没有**。有 = 引脚编号又重复了 |
| b | 让门正常开门，到位时拨动限位 | `LIMIT open edge` 之后电机**立即断电** |
| c | 把 `LIMIT_DEBOUNCE_MS` 临时改成 `500`，再开一次门并拨限位 | 电机仍在**限位触发的瞬间**停，而不是等 0.5 s |

> **(c) 是真正的判据。** 只有轮询时，电机停的时刻会比限位触发晚 `LIMIT_DEBOUNCE_MS`；
> 中断生效时两者几乎同时。把消抖窗口放大到 500 ms 就能用肉眼分辨这两种情况 ——
> 不改这个参数的话，(b) 通过不能证明中断生效。**测完记得改回 25。**

### B. 转储期间必须仍然能停车

修复前 `LOG?ALL` 阻塞主循环约 2 秒，期间 KEY4 急停与命令行 `STOP` **都不生效**。

| 步骤 | 操作 | 预期 |
|---|---|---|
| a | 产生几十条记录后发 `LOG?ALL` | 记录**逐条流式**出现，不是卡住 2 秒后一次性刷出 |
| b | **在输出过程中**长按 KEY4 | **立刻**停电机 + 长鸣（转储继续走完） |
| c | **在输出过程中**在串口敲 `STOP` | 同上 |

> (b)/(c) 就是这项修复存在的理由。转储期间按键没反应 = 分帧没生效、退回阻塞式输出。

### C. 串口命令行必须真的被派发（round 13 真机发现）

修复前**所有**命令都被静默吃掉：接线正常、字节也确实进了 MCU，但收不到任何回包。

| 步骤 | 操作 | 预期 |
|---|---|---|
| a | 上电看串口有没有 `I2C idle : NO (bus held low)` | **必须没有**。有 = `bus_rest()` 又把 SCL 按低了 |
| b | 发 `HELP` | 回 `OK HELP` + 16 行指令表（含 `TRAVEL=<ms>` 与 `SPEED=` 那两行）|
| c | 发一条不存在的命令，例如 `BOGUS?` | 回 `ERR UNKNOWN_CMD (try HELP)`，**而不是沉默** |

> **(c) 才是判据 —— 回错也是回。** 只发 `STATUS?` 会骗人：它的回包和每 10 s 的周期状态行
> 一模一样，无法区分"命令被派发了"和"只是周期行恰好到了"。本轮真的被这一点骗过一次。

### D. 怎么驱动这个命令行

```bat
:: 只监听 12 秒，抓一条周期状态行（周期是 10 秒，所以必须 > 10 s）
powershell -File D:\code\mcp-serial\serial-io.ps1 -Mode read -Port COM7 -ReadMs 12000

:: 发命令并抓回包（安静 600 ms 即返回，一次问答约 1.2 s）
powershell -File D:\code\mcp-serial\serial-io.ps1 -Mode write -Port COM7 -Data "HELP" -ReadMs 8000 -QuietMs 600
```

也可以直接用已注册的 MCP 工具 `serial_list_ports` / `serial_read` / `serial_write`
（定义在 `D:\code\mcp-serial`，已在 `D:\code\.mcp.json` 注册为 `serial`）。

**一次跑完全部 16 项串口功能用例**（含"一行分两次写入"的回归判据、超长行、小写命令、
一次写两条命令、开门/急停链路）：

```bat
powershell -File D:\code\mcp-serial\uart-verify.ps1 -Port COM7
```

> **没接 KEY1 时怎么验证开门动作：** 系统默认未使能，`DOOR=OPEN` 会正确回
> `ERR BUSY (state=IDLE run=0)`。要跑动作链路，可以用 SWD 直接把使能位置 1：
>

> monitor halt
> set var 'Door.c'::s_enabled = 1
> monitor resume
> ```
>

### E. 不按任何键，也能测按键逻辑（SWD 注入事件）

按键是硬件，但"按键驱动的逻辑"完全可以在 SWD 上注入：写 `Key.c` 的事件标志，
让**真实主循环**去消费它。比用手按更可重复，而且把机械抖动排除在外 ——
用杜邦线点触时，"长按没反应"到底是固件门槛还是接触抖动，这样一测就分得清。

逐个按键的事件标志（索引就是 `KeyId_t`）：

| 按键 | 索引 | 注入什么 |
|---|---|---|
| KEY1（启停）| 0 | `set var 'Key.c'::s_keys[0].shortEvent = 1` |
| KEY2（模式）| 1 | `s_keys[1].shortEvent` / `s_keys[1].longEvent` |
| KEY3（开门）| 2 | `s_keys[2].shortEvent` / `s_keys[2].longEvent` |
| KEY4（关门/急停）| 3 | `s_keys[3].shortEvent` / `s_keys[3].longEvent` |

例：验证"KEY3 长按退出日志屏"

```
monitor halt
set var 'Display.c'::s_screen = 2            /* DISP_SCREEN_LOG */
set var 'Key.c'::s_keys[2].longEvent = 1
monitor resume
（等主循环跑一轮：`shell ping -n 2 127.0.0.1 > nul`）
monitor halt
print 'Display.c'::s_screen                  /* 期望 DISP_SCREEN_STATUS */
monitor resume
```

> 注意 `Key_Tick1ms()` 不会清掉这些标志，只有 `Key_TakeShortPress/LongPress()` 会 ——
> 所以注入的事件一定会被主循环消费一次。**注入的是事件，不是电平**，因此
> `holdMs`/消抖窗口都不参与，适合隔离测试"事件之后的逻辑"。

**模拟红外传感器（两个按键）比按键更好用：事件和电平都能注入。**

| 注入 | 写什么 | 代表什么 |
|---|---|---|
| 有人来了（边沿）| `'Sensor.c'::s_outside.event = 1` 且 `.stable = 1` | 传感器输出跳变 |
| **有人站着（只有电平）** | `'Sensor.c'::s_outside.stable = 1`，**不设 event** | **边沿丢失**，只剩电平 |
| 人走了 | 两者都清 0 | 恢复 |

写 `stable` 不会被 1 ms 的 tick 改回去：`Debounce_Tick1ms()` 在"引脚没变 **且** `pending == 0`"
时直接返回，不会用引脚值覆盖它。所以"**边沿丢了、只剩电平**"这个最关键的失效场景可以被精确
复现 —— 门正在关、边沿丢失，仅凭电平也必须反向开门（`Door.c` 的电平兜底，见设计文档 §12.14 附近）。

### F. 一条命令跑完整条链路（62 步）

```bat
powershell -File D:\code\AutoDoor\tools\bench-chain.ps1 -Port COM7
```

它会自己起 OpenOCD（用完释放 ST-Link）、先烧 `build\AutoDoor.elf`（**默认构建**：
`STATUS?` 必须回 `LIMITS=TIMED`，否则它**拒绝开跑**并提示
"-WithLimits only if you actually fitted limit switches"）、把门归一化到"关闭 + 未使能"
（所以**可以反复跑**，不会因为上一轮把门留在 OPEN 而误报），然后依次注入按键与传感器并逐条断言，
最后恢复现场（释放注入、`DELAY=5000`、`MODE=AUTO`、`RESET`）。

覆盖范围：

| 段 | 内容 |
|---|---|
| A 按键 | KEY1 启停、KEY2 切模式、KEY3 开门、KEY4 关门；**MANUAL 模式不会自动关门** |
| B 传感器 | 门外/门内事件各自开门；人走后按 `DELAY` 自动关门 |
| C 防夹 | 关门过程中来人 → **REVERSE 反向开门**（边沿路径）|
| D 电平兜底 | **只有电平、没有边沿**也反向；有人站着就一直不关门 |
| E 拒绝路径 | 遮挡时拒绝关门、急停闩锁、未使能时按键/传感器全部无效，以及**使能后同一个传感器就能开门**（证明门槛才是原因）|
| F 屏幕导航 | 从**任意**非状态屏（事件屏 / 日志屏）长按都能回到状态屏；屏幕内容不上串口，所以用 SWD 读回 `Display.c::s_screen` 再断言 |
| G 运行参数 | `SPEED=` 在 SG90 分支被拒（`ERR N/A - SG90 speed is fixed`）；`TRAVEL=1800` 回 `OK TRAVEL=1800ms (11 us of pulse per 20 ms frame)`，`STATUS?` 里出现 `TRAVEL=1800ms`，低于下限回 `ERR RANGE 600..4000`、非数字回 `ERR BAD_ARG`，`DEFAULTS` 把它复位回 `travel=1500ms` |

> **屏幕有三个**，KEY2 长按循环：状态屏（无标题）→ **事件屏**（`Recent events`）→ 日志屏（`Log n/m`）。
> 没接 EEPROM 时日志屏只有 `(no records)`，**事件屏才是唯一有内容、看起来像"日志"的那一屏** ——
> "长按退不出去"的两次报告都出在这两个屏的区分上。

> `-SkipFlash` 只测板上现有固件，不重新烧录；`-KeepServer` 保留 OpenOCD。
> 断言全部基于固件**实际打印的串口输出**，所以失败时会把"期望什么、实际看到什么"一起打出来。

> **与 `stm32_flash` 的配合：** OpenOCD 的 GDB 服务会**独占总探针**，此时 `st-info` 会报
> `Found 0 stlink programmers`，`stm32_flash` 因"未见探针"拒绝烧录 —— 这不是断线。
> 用 `stm32_gdb` 经 3333 端口 `load` 即可（本轮镜像就是这么烧的）；
> 要用 Keil / CubeProgrammer 时，先 `stm32_debug_server action=stop` 释放探针。
